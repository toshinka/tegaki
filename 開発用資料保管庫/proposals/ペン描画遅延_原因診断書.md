# ペン描画遅延（ディレイ）診断書

調査日: 2026-08-02
調査対象: `tegaki_work/system/emergency-recovery-store.js` / `tegaki_work/core-engine.js` / `tegaki_work/system/project-manager.js`
照合資料: `PROGRESS.md`（既知残存節）/ `開発用資料保管庫/Archive/phase6e.md` / `phase6f.md`
調査担当: Claude

## 0. 結論（先に要点）

**原因は特定できました。ペン入力そのものは実測1ms未満で確定しており、描画エンジン自体は遅くありません。** 遅延の正体は、**バックグラウンドで自動的に動く「緊急復帰（EmergencyRecoveryStore）」のチェックポイント保存処理が、プロジェクト全体をシリアライズしてIndexedDBへ書き込む間、メインスレッドを占有し、その間に来たペンの入力（pointerイベント）がキューで待たされる**ことです。

これは今回の調査で新しく見つかった不具合ではなく、**開発チーム自身がPhase 6eで既に実機計測・記録済みで、現在も「凍結監視」として未解決のまま`PROGRESS.md`に残っている既知課題**です。

> 重いAnimation Projectでは、緊急復旧Project serialization / IndexedDB checkpointとpointer event queue待ちが重なる場合がある。pen / Airbrush確定自体は実測1ms未満だったため、描画結果やHistory上限を変更せず凍結監視する。（`PROGRESS.md`）

そして、この保存処理のコストは**プロジェクト内のレイヤー・フォルダ・CAFの量に比例して重くなる**ため、「フォルダやレイヤーがそれなりに増えた状態で出るものか確信が持てない」というご認識も裏付けられます（後述2章）。

---

## 1. 原因のメカニズム

### 1-1. どのタイミングで走るか

`core-engine.js`で、**History（Undo/Redo）に変更が入るたび**に自動保存の予約が入ります。

```js
this.eventBus.on('history:changed', () => {
    emergencyRecoveryStore.scheduleCheckpoint();
});
```

`history:changed`はストロークの確定、レイヤー・フォルダの追加/削除/並べ替え、塗りつぶし、Motion/WARPのキー編集など、**Undo可能なほぼ全ての操作**で発火します。つまり、描いている間は絶えずこの自動保存が予約され続けています。

### 1-2. 予約の仕組み（デバウンス＋レート制限）

`emergency-recovery-store.js`の`scheduleCheckpoint()`は、変更のたびに1秒のデバウンスタイマーをリセットします。

```js
this._debounceDelay = 1000; // 変更後の遅延 (1秒)
this._saveInterval = 5000;  // 最低保存間隔 (5秒)
...
scheduleCheckpoint() {
    ...
    if (this._debounceTimer) clearTimeout(this._debounceTimer);
    this._debounceTimer = setTimeout(() => {
        this._scheduleIdleAttempt();
    }, this._debounceDelay);
}
```

つまり、**手を1秒以上止めた瞬間**（次のストロークを考えている間、色を選び直している間など）に、`requestIdleCallback`経由で保存処理が動き出そうとします。ストローク中（`isDrawing === true`）は保存を開始しない配慮はされていますが、**保存中に次のストロークを開始した場合、その入力はキューで待たされます。**

### 1-3. 保存処理そのものが重い

実際の保存処理（`performSave()`）は、`window.projectManager.exportProject()`でプロジェクト全体を一度にシリアライズします。

```js
const projectData = await window.projectManager.exportProject();
```

`project-manager.js`の`exportProject()`は、**全レイヤー・全フォルダをforループで同期的に走査**し、さらにアニメーションテーブルのCAF/ClipAsset/Snapshot群も丸ごとシリアライズします。

```js
const layers = this.layerSystem.getLayers();
...
for (let i = 0; i < layers.length; i++) {
    const layer = layers[i];
    const data = layer.layerData;
    if (data.isFolder) {
        projectData.layers.push({ ... });   // フォルダも1件ずつ処理
        continue;
    }
    ...
}
```

このループやアニメーション側のシリアライズ処理には途中で処理を分割してブラウザに制御を返す仕組み（yield）が見当たらず、**レイヤー数・フォルダ数・CAF内部Layer数が増えるほど、この一連の処理は線形に重くなります。** 生成されたデータはさらにIndexedDBへの書き込みも発生します。

### 1-4. 開発チーム自身の実測値

Phase 6eでオーナー自身の重いAnimation Projectで実測された値が記録されています。

> 重いAnimation CAF実測では、Airbrush開始0.1〜0.3ms・確定0.2〜0.7msに対し、緊急復旧はProject export 463.6〜2007.8ms、未使用thumbnail 2514.3〜2726.2ms、全体4378.9〜5698.4msだった。

その後、不要なサムネイル生成を廃止する改善が入りましたが、それでも次の値が残っています（Phase 6e closeout時点）。

> thumbnail廃止後の再測定でもProject export 476.8〜832.4ms、checkpoint全体1896.4〜3766.5msと、直後のpointer queue待ち642.4〜950.5msが残った。

**「pointer queue待ち642.4〜950.5ms」** が、まさにご報告の「ペン描画が遅延する」の実体です。ペン自体の処理（0.3〜0.9ms）ではなく、その直前・直後に走る自動保存のせいで、次のペン入力がブラウザのイベントキューで最大1秒近く足止めされている状態です。

---

## 2. なぜ「フォルダやレイヤーが増えた状態」で出やすいのか

1-3節の通り、`exportProject()`のコストはレイヤー・フォルダ・CAF内部構造の量に線形に比例します。作業を進めてレイヤーやフォルダが増えるほど、

- 保存処理1回あたりの時間が伸びる（Phase 6eの実測で最大2秒以上）
- その間メインスレッドが専有される時間が伸びる
- 結果としてペン入力のキュー待ちが長くなり、体感の遅延が大きくなる

という関係になるため、**「フォルダやレイヤーがそれなりに増えた状態で出るものか」というご認識は技術的に正しい**と考えられます。逆に、レイヤー数が少ない最初のうちは保存が一瞬で終わるため、遅延にほぼ気づけません。

---

## 3. なぜ「時々」なのか

- 1-2節の通り、保存の実行条件は「1秒以上の無操作」かつ「前回保存から5秒以上経過」です。連続してストロークを打ち続けている間は保存が始まらず、**手を止めた瞬間・次のストロークを描き始める瞬間**にちょうど重なりやすい設計です。
- Phase 6eの記録でも「History約10件でも約100件でも、時折入力結果が遅れてから一気に表示される」「件数と遅延の相関は弱い」とあり、**発生タイミングは操作回数ではなく、保存処理と次の入力のタイミングが重なるかどうかに依存する**ため、規則的には再現しにくい性質のものです。

---

## 4. 他に遅延を悪化させ得る付随要素（未確認・仮説レベル）

以下はコード上「あり得る」と判断できるものの、Phase 6eのように実測値が記録されているわけではない、追加の仮説です。優先度は1章の主要因より低いものとして扱ってください。

- **History側の未計上メモリ増加**: `phase6e.md`に記載の通り、各ストロークの前後Rasterスナップショットに加えて`pathsData`（ストローク経路データ）も複製保持されており、この分は現状「宣言byteSizeに含まれていない」ため、長時間描画するほどHistory全体の実メモリ使用量が見た目以上に増えている可能性があります。
- **Clippingマスクの再計算**: レイヤー並べ替えや一部のフォルダ操作のたびに`refreshClippingMasks()`相当の処理が呼ばれており、フォルダ数・クリッピング数が多い状態でこれが頻繁に走ると、保存処理とは別に短い重さが積み重なる可能性があります（前回diagnosisで確認した`_finalizeLayerReorder`経由の呼び出し）。
- **Frame Thumbnailの再生成**: `layer-system.js`にはFrameごとのサムネイル dirty管理があり、レイヤー変更のたびに再生成対象が増えるため、レイヤー数が多い状態ではサムネイル更新の累積コストも無視できない可能性があります。

これらは、もし1章の主要因を解消した後もまだ遅延が残る場合の、次の調査候補として位置づけてください。

## 5. 現状のステータス（凍結監視中・未解決）

Phase 6eではこの問題を認識した上で、次の緩和策のみ実施済みです。

- 自動保存の開始をストローク中は待機させる（`_isDrawingActive()`チェック）
- 復元に不要なサムネイル生成を廃止（4.38〜5.70秒→1.90〜3.77秒に短縮）

一方で、根本原因である「`exportProject()`がプロジェクト全体を同期的に丸ごとシリアライズする」設計自体は変更されておらず、Phase 6f側でも「Project serialization / IndexedDB退避をPhase 6eの凍結監視項目とする」と明記された通り、**意図的に先送りされたまま現在に至っています**。つまり、これは新しいバグではなく、**開発チームが把握しつつも根本対応を保留している既知の設計上のボトルネック**です。

## 6. 推奨アクション

`PHASE4Z_BOUNDARY.md`の枠組みで言えば、`RenderTexture / Snapshot / Preview合成経路の変更`や保存形式に近い変更はCodex側の設計対象です。以下の順で進めることを推奨します。

1. **計測の再取得**: 現在のプロジェクトで実際に`TEGAKI_CONFIG.debug = true`にして`TegakiPerf`ログ（`emergency-recovery.export-project` / `emergency-recovery.total`）を有効化し、実際に遅延を感じたタイミングと自動保存のタイミングが一致するかを確認する。これはコード変更なしで今すぐ検証可能。
2. **短期の緩和策（Codex承認の上でGemini実装可能な範囲）**: `_saveInterval`（現在5秒）や`_debounceDelay`（現在1秒）を、プロジェクト規模（レイヤー数・CAF数）に応じて動的に延ばす、またはプロジェクトが一定規模を超えたら保存頻度を落とす、といった調整。
3. **本格対応（Codex設計必須）**: `exportProject()`自体を分割処理（レイヤーを一定数ごとに`requestIdleCallback`や`setTimeout(0)`で分割してシリアライズする）にする、あるいは差分保存（前回保存からの変更分のみ）に切り替える設計。これは`phase6f.md`が明記する「Phase 6eの凍結監視項目」を正式に再開するタイミングで着手すべき本丸の改修です。
4. **付随要素の検証**: 4章の仮説（History未計上メモリ、Clippingマスク再計算、Frame Thumbnail再生成）についても、同じ`TegakiPerf`診断ログで個別に時間を計測し、主要因（自動保存）を解消した後にまだ体感遅延が残るかどうかで、追加調査の要否を判断する。
