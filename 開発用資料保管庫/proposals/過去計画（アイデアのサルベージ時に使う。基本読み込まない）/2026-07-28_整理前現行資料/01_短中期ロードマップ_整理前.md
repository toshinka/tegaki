### 完了: Phase 6e - 長時間描画・History上限後の重化／クラッシュ調査

- Animation Tableを開かない通常描画でも、描画継続後に遅延増大またはクラッシュする報告を独立再現する。History上限到達が原因とは断定せず、件数上限と推定byte上限、古いentry破棄、RenderTexture / texture cache、pointer sample、event listener、緊急退避の各寿命を分けて計測する。
- 最初の固定条件はHistory 0 / 499 / 500 / 501操作、件数破棄とbyte破棄の双方、pen / eraser / airbrush、通常Layer / CAF working Layer、400×400と大Canvasとする。入力遅延、stroke確定時間、History使用量、常駐texture数、JS heap（利用可能な環境のみ）、console / GPU errorを`TEGAKI_CONFIG.debug`配下で採取する。
- 調査用計測を本番常時ログへ残さず、再現前にHistory classや描画pipelineを再設計しない。上限到達で古い履歴が破棄されてもUndo順、最新stroke、保存／復元が壊れないことを受入条件に含める。
- 長時間連続入力の自動再現は実strokeと同じcommit経路を通し、単なる配列pushの負荷試験で代用しない。ブラウザ／GPU／液タブdriver要因はアプリ側resource増加と分離して記録する。
- Slice 0では`HistoryManager`の上限hit／破棄診断、`byteSize`未宣言entry数、既存stroke profilerのsnapshot / record / finalize時間、active Rasterと累積`pathsData`、JS heap sampleを追加する。通常stroke snapshotが累積`pathsData`も複製する一方、その量が宣言`byteSize`へ含まれない経路を第一監査候補とするが、計測前に削除しない。
- Slice 1ではpixel実byteとpath / point数から見積もるmetadata推定byteを共通化し、stroke / fill / selection / Raster変形・結合のHistoryへ反映した。Historyはtype別使用量を返し、Airbrush / pen opacity / blurの一時textureはdebug終了sampleで残留を追跡する。500件直後の一律crashとは扱わず、実制作で操作種別と長時間状態を比較する。
- 重いAnimation CAF実測ではAirbrush本体より緊急復旧Project exportと未使用thumbnail生成が支配的だった。自動退避をidle開始へ変更し、復元に不要なthumbnailを廃止した。Project export単体の0.46〜2.01秒とheap約2.4GBは、実crash未再現のまま描画pipelineを変えずPhase 6fの容量preflightへ引き継ぐ。
- thumbnail廃止後もProject export 0.48〜0.83秒、checkpoint全体1.90〜3.77秒、pointer queue待ち0.64〜0.95秒が重なった。保存頻度・復旧保証を即席に弱めず、Project serialization / IndexedDB退避を凍結監視し、Phase 6fの共通peak memory監査後に再開する。

### 完了: Phase 6f - Motion / WARPのLayer構造保持Bake・容量耐性

- 現行の完成Clipを1 Frame 1 Rasterへ展開する非破壊Bakeは、専用の新Laneを最上段へ挿入して元Clipを下段で非表示保持する軽量入口として維持する。別buttonのLayer構造保持Bakeは、CAF内部Layer / Folder構造をFrameごとに独立複製する編集可能BakeとしてSlice 1で実装した。
- Layer構造保持Bakeは各Rasterを個別変形せず、整数Frameの既存Motion / WARP sampleを1 Frame Clipの静的transformとFrame 0 deformer keyへ畳み込む。これにより`内部Layer評価 → Folder clipping / blend → Clip Motion / WARP`の現行順を変えず、normal / inverse clipping、非NORMAL blend、半透明を近似しない。Physics有効、Snapshot欠損、容量超過は構造保持を開始せず理由を表示し、現行flatten入口を残す。
- Frame数・実効Layer数・tight Raster bytes・History・preview texture・Project export展開を含むpeak memoryを開始前に見積る。全Frame全Layerのpixel配列一括常駐を避け、逐次複製、独立Snapshot、原子的rollbackを実装済み。中止操作も同じbefore stateへ戻し、新Lane / Asset / SnapshotとHistoryを残さない。
- Slice 2で複合Folder、normal / inverse clipping、各blend、半透明、欄外Rasterの構造保持Bakeと現行flatten Bakeを実像比較し、いずれも元表示とpixel差分0、APNG / GIF preview一致を確認した。外部Project実再読込と400×400・1 Layer・240 Frame構造保持Bakeも完走し、推定peak 1381MB、観測heap増加144MB、最上段Lane、元Clip非表示、History 1件、console warning / error 0件を確認した。直後の同期checkpointで強いmemory pressureを観測したため、校正済み安全上限を1GiBへ固定し同構成は開始前拒否へ変更した。
- 詳細正本は`09_変形アニメーション・メッシュ・GPU画材ロードマップ.md`の「Layer構造保持Bakeと容量gate」。現行flatten入口と構造保持入口を分離し、Phase 6c / 6dの座標・mask・sampling正本を共有する。

### Animation / transform

- Phase 5wから5z6でposition / scale / rotation / anchor、opacity、Clip blend、cubic-bezier sampling、preset、Segment Easing Editorを既存 `transformKeyframes` 正本へ段階実装した。
- Segment Easing Editorは1区間の進捗曲線、Motion GraphはClip全体のparameter実値、Motion PathはCanvas上のXY経路として分ける。Canvas、数値 / marker、graphの各編集面から同じkey正本を操作し、UI固有のsample列を保存しない。
- Motion Graphはread-only viewer、preset拡張、既存key編集、curveを保つ途中点追加の順で検証する。詳細は `10_Motion_Graph・Easing・Motion_Path設計.md` を正本とする。

- Ctrl複数選択CAFのDURATION一括増減は、同じdeltaを原子的に適用するTegaki側候補とする。Groupの位置・間隔を含む時間比例retimingは引き続き動画WEBUI側に置く。総Frames不足時はFRAMES増加を案内する。
- Ctrl+dragによるCAF矩形選択 / 解除は複数選択の次候補とする。空白開始だけをmarquee入口にし、既存CAF移動、Timeline pan、retiming handleと競合させない。加算 / 解除はdrag開始時のCtrl状態と交差CAF集合から一度だけ確定し、pointermoveごとにTimeline正本を変更しない。
- CAFを跨ぐ内部Layer移動は、まず既存の内部Layer copy / pasteを原子的な「複製後にsource削除」へ組み合わせられるか監査する。ClipAsset共有、Folder parent、clipping source、Snapshot ID、Undo / Redoの全体成功が保証できない場合は直接D&Dを実装せず、copy / pasteを正式入口として維持する。
- 複数CAFまたは上下LaneのCAF合成は低優先度候補とする。実装する場合は元CAFを残す非破壊mergeを既定とし、Lane順、Clip Motionのbake、opacity / blend、異なるduration、共有ClipAssetを先に契約化する。Lane eye横の専用buttonは必要性が実制作で確認されるまで追加しない。
- 簡易warp / morphは少数control pointと自動weightを優先し、密な手打ちmeshから始めない。
- Bone、Perform記録、physicsはwarpとkeyframe安定後まで保留する。
- 詳細は `09_変形アニメーション・メッシュ・GPU画材ロードマップ.md` を正本とする。

### 長期候補: 別動画WEBUIとの連携

- Tegaki完成後に、After Effects的な動画編集を別ウィンドウ・別WEBUIとして構築する案を保留する。Animation Tableを分離するより、描画と動画編集のUI密度・操作契約を互いに独立させやすい。
- TegakiからはCAFまたはCAF Groupを、動画側からは使用clipをCAFへ分解可能な交換形式で受け渡す。初期段階は明示的な送信・取込とし、同時編集や自動同期を前提にしない。
- Group時間比率伸縮は動画側のkeyframe/retiming機能として扱い、Tegaki側Groupへは持ち込まない。動画側から戻す時に、整数FrameへbakeしたCAF列として変換する案を優先する。
- 難度は、片方向のCAF素材送信が中、Group構造を保った往復が高、動画clipから編集可能なCAF・Layerへ可逆分解する往復が非常に高い。主な難所はAsset/Snapshot参照、FPS・時間丸め、effect/transformのbake、色・alpha、変更競合、version互換である。
- 最初の実証は `manifest + raster frame sequence + timing + stable asset id` 程度に絞り、同一ブラウザ内では `BroadcastChannel` または明示ファイル受け渡しをtransport候補とする。保存形式のversioningをUI連携より先に決める。
