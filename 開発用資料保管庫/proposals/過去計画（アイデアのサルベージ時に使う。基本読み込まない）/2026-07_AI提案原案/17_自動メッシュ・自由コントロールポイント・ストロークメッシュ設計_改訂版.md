## 2. 最終的に目指す制作体験

本計画群の最終的な着地点は、単に三角形Meshを編集できることではない。

目標は、ユーザーがパーツを描く、またはCAF内Folderへ分けるだけで、最小限の操作からBONE付きの柔軟なキャラクターアニメーションを作れることである。

### 2.1 目標体験

```text
パーツを描く / CAFへ整理
  ↓
輪郭・PrimitiveCage・Ribbon等を自動生成
  ↓
BONEを配置
  ↓
自動Binding / 初期SkinWeight
  ↓
必要な箇所だけweight調整
  ↓
手・足・頭などを直接動かす
  ↓
BONE階層とMeshが連動
  ↓
伸縮・曲げ・追従を含むアニメーションを即座に作成
```

目指す利用感は、例えば次のようなものである。

- 腕や脚へBONEを置くだけで、Meshが同時に曲がる
- 手を移動すると、肘や肩も一定割合で追従する
- 腕を伸ばす設定ならMeshも伸びる
- 伸ばさない設定なら骨長を維持する
- stretchを一部だけ許可できる
- 指定したFrame区間だけconstraintを有効にできる
- weightを手動調整して肩、肘、衣服、髪の影響範囲を修正できる
- 初期MeshやCageが自動で存在するため、点を一から配置しなくても開始できる
- 単純な図形的キャラクターなら、自動生成とBONE配置だけで「ゴム人間」のような走行アニメーションを短時間で作れる

### 2.2 本書の責任範囲

本書17の中心責任は次である。

- TriangleMeshの保存正本候補
- MeshVertexとControlHandleの分離
- Mesh生成方式
- Binding / SkinWeightの候補
- BONEから受け取る変形入力の契約
- GPU previewとCPU/exportの一致
- Topology変更とAnimationの整合

次は主としてボーン設計側、または統合Phaseの責任である。

- BONE階層
- FK
- 手を動かして肩が追従するIK／逆方向constraint
- stretchの許可・禁止・上限
- constraint weightのFrameキー
- 指定区間だけconstraintを有効にするTrack
- 子・孫操作から親へ影響を分配するchain solver
- BONEとCAF内部Partの所有関係
- Dynamic Draw Order

これらは将来の`15_ボーン・CAF階層パーツ・動的描画順制御設計_改訂版2`等で再整理する候補である。

ただし本書は、将来統合できるようMesh側の接続要件を定義する。

## 4. MeshVertexとControlHandleを分離する

### 4.1 必須概念

TriangleMeshの描画頂点と、ユーザーが操作する少数点は同一とは限らない。

```text
ControlHandle
  少数
  ユーザー操作対象
  キーフレーム対象候補

MeshVertex
  多数
  triangle描画対象
  UVを保持
  通常は直接キーフレーム化しない

Binding
  ControlHandle / BONEからMeshVertexへの影響
```

### 4.2 直接頂点編集方式

候補A:

```text
ControlHandle = MeshVertex
```

利点:

- 実装が比較的単純
- weight計算が不要
- Delaunay結果を直接編集できる
- prototypeに適する

欠点:

- 頂点数がそのまま操作点数になる
- Animation keyが増える
- 密Meshでは操作しにくい
- 「少数点で柔軟に動かす」という目標に届かない

### 4.3 Sparse Handle方式

候補B:

```text
少数ControlHandle
  ↓ Binding
多数MeshVertex
```

利点:

- 少数点で変形できる
- BONE連動へ接続しやすい
- 自動Meshを密にしてもUIが過密にならない
- weight調整を導入できる

欠点:

- Binding生成が必要
- weight編集UIが必要
- topology変更時の再Binding契約が必要
- CPU/GPUで同じ評価を実装する必要がある

### 4.4 CODEX判断

初期prototypeでは候補Aを採用してよい。

ただし本番到達点は候補BまたはBONE Skinningを含むHybrid方式を基本候補とする。

「自由点追加＋Delaunay」を採用するだけで、少数ControlHandle変形が完成したとみなしてはならない。

## 7. Mesh生成方式の提案群

## 7.1 Manual Triangle Mesh

ユーザーがMeshVertexを追加し、三角形接続を作る方式。

### 候補操作

- vertex追加
- vertex移動
- vertex削除
- edge追加
- edge削除
- triangle追加
- triangle削除
- boundary指定
- hole指定
- component分離
- triangulation再実行
- validation

### 利点

- 最小機能を検証しやすい
- 自動生成アルゴリズムへ依存しない
- topologyとrender backendの正しさを確認できる

### 制限

- 最初から利用者向け主機能にしない
- 密な点配置を要求しない
- weightなしの場合は直接vertex poseとなる
- 初期prototype向け

---

## 7.2 Delaunay Points

ユーザーが点を置き、自動三角形化する方式。

### Plain Delaunayの制限

通常のDelaunayは入力点群の凸包を三角形化する。

そのため、次を自動では守らない。

- 凹輪郭
- hole
- 複数island
- 明示的な境界edge
- 細長い隙間
- 接続してはいけないcomponent

### 採用候補

#### 案A: Convex Cageとして使う

輪郭追従Meshではなく、画像全体を包む変形Cageとする。

利点:

- 最も単純
- 少数点で扱える
- 透明余白を含んでも変形Cageとして許容できる

#### 案B: Boundary Edgeをユーザー指定する

点だけでなく、外周edgeまたはloopを明示する。

その後にConstrained Triangulationを行う。

#### 案C: Alpha Contourを境界として利用する

輪郭抽出はAutoContour Generatorへ任せ、Delaunayは内部点充填に限定する。

#### 案D: Delaunayを編集補助に限定する

自動triangle候補を表示し、ユーザーが確定・削除する。

CODEXはprototype結果から用途を決める。

### 必須edge case

- 3点未満
- 重複点
- 近接点
- 同一直線
- 極小triangle
- 同一円周上
- 不正winding
- triangle overlap
- point追加順の差
- deterministic tie-break

---

## 7.3 Auto Contour Mesh

合成済みtextureまたは明示したsource snapshotのalphaからMeshを生成する方式。

### 処理候補

```text
alpha readback
  ↓
threshold
  ↓
connected components
  ↓
outer contour / holes
  ↓
contour simplification
  ↓
boundary vertices
  ↓
interior point generation
  ↓
constrained triangulation
  ↓
UV
  ↓
validation
```

Marching Squaresは輪郭抽出候補であり、三角形充填そのものではない。

### 対応すべき要素

- anti-alias境界
- 半透明pixel
- 柔らかいbrush
- hole
- island
- thin line
- isolated pixel
- small noise
- contour self-intersection
- source bounds offset
- transparent padding
- threshold変更
- simplification tolerance

### 初期制限候補

- 単一DrawingSnapshot
- 単Frame Clip
- または明示Bind Frame
- 完成texture一枚
- alpha threshold固定preset
- 最大vertex数
- 最小island面積

multi-frame CAF全体のunion contourは後続研究へ送る。

### 表現上の注意

「輪郭へ完璧に追従する」とは記載しない。

正しくは次とする。

> 指定alpha threshold、簡略化誤差、頂点上限に基づいて表示形状を近似する。

## 7.4 Primitive Cage

ユーザーが点を一から置かなくても、初期状態から制御形状を自動で持てるようにする方式。

これは目標とする「自動生成とBONE配置だけで即座に動かす」体験に重要である。

### 候補Primitive

- Box Cage
- Rounded Box
- Capsule
- Strip
- Radial
- Limb
- Tail / Hair Chain
- Face Oval
- Cloth Patch

### 自動選択候補

source bounds、aspect ratio、alphaの主軸、細長さから初期形状を選ぶ。

例:

```text
細長い横形状 -> Strip / Capsule
細長い縦形状 -> Limb
ほぼ円形 -> Radial
矩形 -> Box
不規則 -> Alpha Contour
```

### 利点

- 操作開始が速い
- 自動輪郭より計算が軽い
- topologyが安定する
- BONEとの初期Bindingを作りやすい
- 小さな図形キャラクターに向く

### 欠点

- 複雑な輪郭へは近似的
- transparent paddingの扱いが必要
- source変更に追従しない場合がある

Primitive CageとAutoContour Meshは排他的でなく、用途別に併存してよい。

## 7.5 Ribbon Mesh

腕、脚、髪、尾、リボン、触手などの長細い形状を対象とする。

### GuideStroke

入力strokeは描画データではなく、Setup用の非破壊guideとする。

```text
GuideStroke {
  points[]
  widthMode
  startWidth
  endWidth
  sourceRevision
}
```

### Ribbonの正本候補

```text
RibbonSample {
  center
  tangent
  normal
  halfWidth
}
```

Render Vertex:

```text
left  = center - normal * halfWidth
right = center + normal * halfWidth
```

### 必須処理

- centerline resampling
- tangent
- normal continuity
- cusp検出
- direction reversal
- miter limit
- bevel / round join
- start / end cap
- self-intersection検出
- width sampling
- UV割当
- source alphaへの幅推定

### 幅推定案

#### 案A: ユーザー指定

一定幅または始点・終点幅を設定する。

#### 案B: Alpha探索

GuideStrokeの法線方向へalpha境界を探索する。

#### 案C: AutoContour連携

既存contourとGuideStrokeの交差から左右幅を得る。

#### 案D: Primitive Limb

初期capsule幅を自動生成し、ユーザーが調整する。

法線スムージングだけで自己交差や幅保持が保証されるとは記載しない。

## 8. BindingとWeight

### 8.1 最終目標

BONEを曲げた際、関連Meshも同時に変形する。

各MeshVertexは、1つ以上のBONEまたはControlHandleから影響を受ける。

```text
deformedVertex =
  weighted combination of influencing transforms
```

### 8.2 候補方式

#### 案A: Linear Blend Skinning

各BONE行列をweightで合成する。

利点:

- 一般的
- CPU実装しやすい
- weight paintingと相性がよい
- BONE階層へ接続しやすい

課題:

- 大きく曲げた関節で体積が痩せる
- scaleとrotationの混合
- 2D affine合成の順序

#### 案B: Segment Distance Weight

頂点からBONE segmentまでの距離で初期weightを生成する。

利点:

- 自動生成が比較的単純
- 腕・脚・Ribbonに向く

課題:

- 隣接しないBONEへの漏れ
- holeやisland
- 関節周辺の調整

#### 案C: Heat / Harmonic系Weight

Mesh topologyを考慮してweightを拡散する。

利点:

- 複雑形状へ自然に広がる可能性
- 輪郭内で影響を制御しやすい

課題:

- 実装と数値計算が重い
- browser上での性能
- hole、component
- 再計算とdeterminism

#### 案D: Cage Coordinates

少数ControlHandleまたはCage Vertexから内部頂点を変形する。

利点:

- 少数点操作
- Primitive Cageと相性がよい
- BONEをCageへ接続できる

課題:

- 方式選択が必要
- 凹Cage
- self-intersection
- CPU/GPU一致

#### 案E: Hybrid

- BONE Skinningを基本
- 関節周辺は補助ControlHandle
- Ribbonは専用幅保持評価
- 顔や衣服はCage
- 最終補正をweight brushで行う

最終的な制作体験に最も近いが、最初から全て実装しない。

### 8.3 Weight規則

最低限定義する。

- weight合計
- 0 weight fallback
- 負weightの可否
- 1頂点の最大影響数
- normalized / unnormalized
- locked influence
- componentをまたぐ影響禁止
- hidden Boneへの影響
- deleted Bone
- topology revision変更時の再計算
- save精度
- deterministic order

MVP候補:

```text
weight >= 0
sum(weights) = 1
max influences = 4
0 weight時はrest位置
```

値はprototypeと性能調査後に確定する。

## 10. BONE連動インターフェース

本書はBONE solver自体を確定しない。

Mesh側は、各FrameでBONE評価結果を受け取り、同じ結果をpreview、playback、onion、exportへ渡せることを目標とする。

### 10.1 入力候補

```text
EvaluatedBonePose {
  boneId
  bindWorldMatrix
  poseWorldMatrix
  deformMatrix
  stretchRatio
  activeWeight
}
```

Mesh evaluatorはBONE階層を直接解決せず、BONE側が評価済みposeを渡す方式を第一候補とする。

### 10.2 変形行列

候補:

```text
deformMatrix =
  poseWorldMatrix
  * inverse(bindWorldMatrix)
```

各頂点はbindingに従って複数行列の影響を受ける。

正確な2D affine blend方式はCODEXがprototypeで確認する。

### 10.3 Stretch

BONE側から受ける候補値:

- `stretchRatio`
- `stretchEnabled`
- `stretchMin`
- `stretchMax`
- `stretchWeight`

Mesh側は、stretchをBone軸方向だけへ適用する案、通常行列へ含める案、Ribbon width compensationを併用する案を比較する。

### 10.4 Parent Follow / IKとの境界

「手を動かすと肩も動く」は通常のFKではなく、IK、chain constraint、distributed follow等の領域である。

候補:

```text
End Effector Drag
  ↓
Chain Solver
  ↓
手首・肘・肩のpose
  ↓
EvaluatedBonePose
  ↓
Mesh Skinning
```

Mesh側はsolver方式を知らず、評価済みBONE poseを受け取る。

### 10.5 区間指定

「指定区間だけ動く」「指定区間だけ伸びる」はBONE／constraint側のTrackで管理する候補とする。

例:

```text
constraintWeightTrack
stretchWeightTrack
followWeightTrack
ikBlendTrack
```

Mesh側はFrameごとの最終`activeWeight`や`stretchRatio`を受け取る。

この責任分離により、BONE設計がFK、IK、親追従、部分追従のどれを採用しても、Mesh evaluatorを作り直さずに済む。

## 12. Source変更とMesh状態

Mesh生成後にsource画像が編集されると、Meshが古くなる。

### 12.1 状態候補

```text
VALID
  source revision一致

STALE
  sourceは変更されたがMeshは使用可能

INVALID
  source参照、bounds、Bind Frame等が失われた
```

### 12.2 無言再生成禁止

自動再生成すると次が壊れる可能性がある。

- vertex ID
- triangle index
- SkinWeight
- ControlHandle Binding
- Animation key
- Weight手動編集
- Bone association

そのため、source変更時に無言で再生成しない。

### 12.3 再生成選択肢

- 現Meshを維持
- 全再生成
- contourだけ更新
- interior vertexだけ再生成
- weightを保持してTopology再生成
- weight再生成
- Animation keyを破棄して再生成
- キャンセル

実装可能範囲はCODEXが決定する。

初期MVPでは「現Mesh維持」または「全削除して再生成」に限定してよい。

## 24. 最終提案

本計画の最初の着地点は次とする。

> 固定されたTriangleMeshを単一textureへ非破壊適用し、保存、History、preview、playback、onion、exportで同じ結果を出す。

次の着地点は次とする。

> MeshVertexとControlHandleまたはBONEをBindingし、自動weightと手動weight調整によって、BONE変形へMeshを追従させる。

最終的な統合目標は次とする。

> パーツを描く、またはCAF Folderへ整理した後、Primitive Cage、AutoContour、Ribbon等から初期Meshを自動生成し、BONEを配置するだけで初期SkinWeightが作られ、必要な部分だけweightを修正して、曲げ、伸縮、IK、親追従を含むキャラクターアニメーションを短時間で作成できる。

本書はMesh側の提案を扱う。

手を移動した際に肩まで追従するchain solver、stretch制限、区間別constraint、子・孫から親への影響については、BONE計画の改訂版または15・16・17の統合Phase計画で再定義する。
