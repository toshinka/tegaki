## 2. 解決したい課題

現在のTransform Motionは、フレームごとに位置キーを手動指定することで精密に制御できる一方、自然な軌跡や演技タイミングを多数のキーとして入力する場合は作業量が大きい。

モーションパフォームは、キャンバス上で対象を掴んで動かす操作を、Clip Motionの位置キーへ変換することで、次を実現する。

- 直感的な位置軌跡入力
- 速度変化や停止区間を含む演技付け
- 短いClipでも、入力者が急いで操作する必要のない相対時間記録
- 手打ちキー作業の軽減
- 既存Clip Motion、Timeline、History、preview、exportへの統合

ただし、ゆっくり操作できることと、入力中の局所的速度差を無視できることは同じではない。

曲線を正確に描くためにユーザーが減速した場合、その減速もMotionタイミングとして記録される。MVPはこの特性を明示した上で、単一ジェスチャー方式として提供する。

## 3. コア概念: 正規化相対時間

pointerdownから操作終了までの入力時間を `T_total` とし、各サンプル時刻 `t_i` を次の比率へ変換する。

```text
r_i = t_i / T_total
0.0 <= r_i <= 1.0
```

この比率を選択Clipのローカル時間へ割り当てる。

これにより、例えば24フレームのClipに対して、入力者が2秒で操作しても10秒で操作しても、操作全体がClipの先頭から終端へ収まる。

保持されるのは絶対秒数ではなく、ジェスチャー全体に対する相対的な速度変化と停止時間の割合である。

### 3.1 初期範囲契約

MVPでは記録範囲を選択Clip全体に固定する。

```text
対象開始 = Clip local frame 0
対象終了 = Clip local frame frameCount - 1
```

この契約では、総Frames不足による自動拡張は発生しない。

したがって旧提案にあった「Frames不足時に確認して拡張する」仕様はMVPから削除する。

将来、現在FrameからOUTまで、IN/OUT範囲、選択時間範囲などを導入する場合にのみ、自動拡張禁止契約を再検討する。

## 4. 入力キャプチャ設計

### 4.1 PointerEventだけに依存しない

pointerが完全に静止している間、`pointermove`が発生しない場合がある。

そのため、PointerEventの到着時刻だけを記録すると、ストローク途中の停止区間を正しく復元できない。

採用候補は次の二経路構成とする。

```text
PointerEvent / getCoalescedEvents()
  └─ 最新pointer位置を更新
  └─ 高密度移動サンプルを補助取得

固定時計 sampler
  └─ 現在位置と経過時間を一定周期で記録
  └─ pointerが停止中でも同じ位置を継続記録
```

固定時計には`requestAnimationFrame`または既存runtime tickを利用する候補があるが、CODEXは現行の描画・Motion gesture経路を調査して決定する。

### 4.2 記録するruntimeデータ

```text
RawPerformSample {
  elapsedMs
  screenX
  screenY
  worldX
  worldY
  source
}
```

`source`は必須保存項目ではなく、debug時に次を区別する候補である。

- `pointer`
- `coalesced`
- `clock`
- `pointerup`

Raw SampleはProjectへ保存しない。

### 4.3 入力終了・キャンセル

必須処理対象:

- `pointerup`
- `pointercancel`
- `lostpointercapture`
- Escape
- window blur
- 対象Clip削除
- Project切替
- mode切替
- popup close
- 異常に短いtap
- `T_total = 0`または分母に使えない短時間入力

キャンセル時は、Project、Timeline、Historyへ変更を残してはならない。

### 4.4 CODEX調査: pointer処理

CODEXはPhase 7計画作成前に次を確認する。

- 現行Canvas Motion dragのpointer所有者
- `setPointerCapture()` / `releasePointerCapture()`の既存契約
- `getCoalescedEvents()`の既存利用箇所
- 高Hz入力の集約方法
- `pointercancel`、blur、Escapeの共通処理
- Canvas上のモード排他管理
- overlayのmount先とdispose契約
- Vキー変形gestureとの共通化可能範囲

新しいpointer基盤を独立実装するのは、既存経路を再利用できないと確認された場合に限る。

## 5. 座標変換とGrab Offset

### 5.1 pointer絶対座標をMotion `x / y`へ直接格納しない

Motionの`x / y`はpointerの絶対位置ではなく、Clip transformの位置成分である。

pointerdown位置がClipのpivotと一致するとは限らないため、絶対pointer座標を直接`x / y`へ設定すると、記録開始時にClipがジャンプする。

### 5.2 基準値

pointerdown時に次を固定する。

```text
baselineTransform = 現在Frameで評価されたClip transform
initialPivotWorld = baselineTransform適用後のpivot world座標
initialPointerWorld = pointerdownのworld座標
grabOffset = initialPointerWorld - initialPivotWorld
```

入力中:

```text
desiredPivotWorld = currentPointerWorld - grabOffset
deltaWorld = desiredPivotWorld - initialPivotWorld
performedPosition = baselinePosition + deltaWorld
```

実際の式と使用helperは現行Clip Motion実装に合わせる。

### 5.3 座標系の再利用

次を新規実装してはならない。

- screen→world変換
- Camera zoom補正
- Camera pan補正
- Canvas local変換
- pivot inverse matrix
- anchorを含む表示行列
- static transformとsampled transformの合成順

CODEXは既存のClip Motion drag、`coordinate-system.js`、transform anchor関連処理を追跡し、同じhelperを利用する。

### 5.4 CODEX調査: 座標系

- Motion Canvas dragがscreen差分をどこでworld差分へ変換しているか
- Camera zoom・panを含む共通helper
- Clipの静的transformとMotion sampled transformの所有関係
- anchor変更時の表示維持処理
- popup内previewと通常Canvasで同じ座標契約を使っているか
- pointerdown時のgrab offsetに相当する既存処理
- Clip local frameとProject frameの変換位置

## 6. Frame Resampling

### 6.1 サンプルをフレームへ丸めない

旧提案では、各Raw Sampleを次の式でフレームへ量子化していた。

```text
round(r_i * frameCount)
```

この方式は次の問題を持つ。

- 終端側の複数区間が最終フレームへ偏る
- 入力デバイスのイベントHzで結果が変わる
- 同一フレームで最後の点を採用すると値が後方へ偏る
- サンプルが少ない場合にフレームが欠ける

採用候補は、各Frame時刻から連続軌跡を評価する方式とする。

### 6.2 Frame時刻

`frameCount >= 2`の場合:

```text
r_k = k / (frameCount - 1)
k = 0 ... frameCount - 1
```

これにより、

```text
先頭Frame -> r = 0.0
最終Frame -> r = 1.0
```

が保証される。

単Frame ClipではMotion Performを無効とし、理由をUIへ表示する。

### 6.3 連続軌跡

正規化Raw Sample列から、時刻 `r` に対する位置関数 `P(r)` を構成する。

MVPの第一候補は、隣接Raw Sample間の時間線形補間とする。

```text
P(r) = lerp(sampleA.position, sampleB.position, localRatio)
```

ただし、停止区間を正しく扱うため、固定時計sampleによって同一位置の時間範囲が入力列へ含まれている必要がある。

### 6.4 出力

各Clip-local Frame `k`について一つの位置値を生成する。

```text
densePosition[k] = P(r_k)
```

入力イベント数にかかわらず、同じ時刻付き軌跡なら同じFrame値になることを受け入れ条件とする。

## 7. Hold区間の扱い

### 7.1 Hold内部の全キーを保持する必要はない

位置が変化しない区間で、すべての中間Frameキーを残す必要はない。

必要なのは次である。

- Holdへ入る境界
- Holdから出る境界

両境界の位置が等しければ、その間はLINEAR補間でも停止状態を維持できる。

### 7.2 旧提案のRDP説明修正

「時間–値グラフ上の水平線なのでRDPで削除されない」という説明は誤りである。

通常のRDPでは、水平線上の中間点は冗長点として削除される。

正しい契約は次とする。

> Hold区間内部の冗長点は削除してよい。ただし、移動から停止へ変わる境界と、停止から移動へ戻る境界を必須点として保護する。

### 7.3 Hold境界検出

将来の簡略化Sliceでは、project pixel基準またはworld距離基準の速度閾値を使用し、Hold entry / exitを検出する。

閾値は固定値で決めず、CODEXが次を調査した上で決定する。

- Project解像度
- Camera zoomに依存しない座標単位
- 344×135など小Canvasでの1pixel誤差
- 400×400上限時の許容差
- pen jitter
- mouse jitter
- devicePixelRatio

## 8. 現行Motionキーモデルとの整合

### 8.1 複合キー問題

現行Motionキーが`x`と`y`だけの独立トラックではなく、位置、拡縮、回転、不透明度、blendなどを一つのキーへ保持する場合、Performが空白Frameへ位置キーだけを追加することはできない。

対象外parameterの区間補間を分断し、見た目を変える可能性があるためである。

CODEXは実コードで現在のMotion key schemaを確認する。

### 8.2 Dense Composite-Key Bake候補

複合キー構造が現行正本である場合、MVPの安全候補は次とする。

各対象Frameで現行transformをsampleする。

```text
existing = sampleClipTransform(clipInstance, frame)
```

その結果の`x / y`だけをPerform値へ置換する。

```text
generatedKey = clone(existing)
generatedKey.frame = frame
generatedKey.x = performedX
generatedKey.y = performedY
```

これにより、少なくとも整数Frame上では対象外parameterの表示値を維持できる。

### 8.3 破壊性の明示

この処理は、既存の少数キーとEasingを、対象範囲の密な複合キーへBakeする可能性がある。

したがってUIでは「位置キーだけを追加」と説明しない。

候補説明:

> 対象ClipのMotionをフレーム単位へ変換し、位置をPerform結果へ置き換えます。回転・拡縮・不透明度などは現在の各フレーム表示値を維持します。既存の区間Easing編集情報は失われる場合があります。

### 8.4 CODEX調査: Motion schema

- Motion keyの実スキーマ
- 同一Frameへのキーmerge規則
- `sampleClipTransform()`相当APIの所有者
- 暗黙始点・暗黙終点
- HOLD / LINEAR / Bezierの所有規則
- 左キーが右区間を所有するか
- Easingがparameter共通か
- Motion key clone / validation方法
- Clip retiming時のキー再配置
- copy/paste時のMotionキー処理
- save/load schema
- old Project migration
- playback、onion、exportが同じsamplerを使うか

## 9. キーフレーム簡略化

### 9.1 MVPでは簡略化を必須にしない

Phase 7の最初の実用版はDense Keysを許容する。

理由:

- 正しさを検証しやすい
- 現行samplerとの一致を比較しやすい
- 複合キーの副作用を観測しやすい
- Undo/Redo、save/load、export不一致を切り分けやすい
- Bezier fittingの複雑性を持ち込まない

性能と編集性の評価後に、別Gateで簡略化を導入する。

### 9.2 X/Y独立RDPは採用しない

`x(frame)`と`y(frame)`を独立に簡略化すると、残るFrame集合が異なる。

複合キーへ戻すにはunionを作る必要があり、さらに現行EasingがX/Y共通の場合は個別曲線を表現できない。

そのため、初期案としてのチャンネル別RDPは不採用とする。

### 9.3 採用候補: 時間パラメータ付きXY誤差簡略化

区間`[a, b]`を仮定し、その間の各Frameについて、区間両端から得られる予測XYとDense結果のXYを比較する。

```text
error(k) = distance(predictedXY(k), denseXY(k))
```

最大誤差が許容値以下なら中間キーを削除できる。

これは単純な空間RDPではなく、Frame時刻を固定した位置軌跡簡略化である。

必須保護点:

- 先頭
- 終端
- Hold entry
- Hold exit
- 方向反転
- 速度符号変化
- 大きな曲率変化
- 既存明示キーとの境界

### 9.4 簡略化の失敗時

簡略化前後を全対象Frameで比較し、許容誤差を超えた場合はDense Keysを維持する。

簡略化は必ず出力最適化であり、記録結果を近似するための必須処理ではない。

## 10. EasingとBezier自動フィット

### 10.1 Phase 7 MVPではLINEAR

初期出力の補間は原則LINEARとする。

既存MotionキーのEasing契約によっては、Dense Keyの各区間をLINEARへ固定することで、Frame間の予測不能なovershootを避ける。

### 10.2 Cubic Bezier自動フィットを後続研究へ送る

Bezier自動フィットには次の未解決事項がある。

- XとYに共通の進捗率を適用できるか
- 曲線形状を直線区間＋Easingだけで近似できるか
- direction reversalを一つのBezier区間に入れないか
- overshootを許可するか
- 既存rotation、scale等の区間Easingを壊さないか
- parameter共通Easing契約と両立するか
- 左キー区間所有規則を維持できるか
- Segment Easing Editorへ自動生成結果を表示する意味があるか

このため、旧Slice 3の「チャンネル別RDP＋Bezier自動フィット」はPhase 7 MVPから除外する。

## 11. 上書き・Preflight・確認

### 11.1 確認時点

既存キーが対象範囲に存在する場合、gesture完了後ではなくPerformモード開始前にpreflightを行う候補とする。

理由:

- ユーザーが操作後に破壊的変換を知ることを避ける
- Easing消失の可能性を事前に伝えられる
- Project変更前にキャンセルできる
- Capture中の確認popupを避けられる

### 11.2 確認が必要な条件

CODEXは実コード調査で条件を確定するが、候補は次である。

- 対象範囲に明示Motionキーが存在する
- LINEAR以外のEasingが存在する
- HOLD区間が存在する
- Clip retiming済みである
- 他parameterのMotionが存在する
- 複合キーBakeによって編集構造が変わる

### 11.3 確認文候補

```text
この操作は対象ClipのMotionをフレーム単位のキーへ変換します。

位置はPerform結果へ置き換えられます。
回転・拡縮・不透明度などは、現在の各フレーム表示値を維持して保存されます。

既存の区間Easingや少数キー構造は失われる場合があります。
```

既存キーがなく、空のMotionへ位置のみ生成できる場合は確認不要とする候補がある。

### 11.4 自動拡張禁止

MVPはClip全長へfitするため自動拡張しない。

将来、指定時間範囲がClip終端を越える機能を追加する場合も、無言のFrame拡張は禁止し、明示確認を必要とする。

## 12. HistoryとMutation責務

### 12.1 一操作一履歴

```text
1 Perform gesture = 1 Timeline History entry
```

pointermoveごと、Frameごと、キーごとにHistoryを積んではならない。

### 12.2 Capture中はProjectを変更しない

MVPの安全候補:

1. pointerdown時にbefore snapshotを取得
2. Capture中はruntime overlayとpreviewだけ更新
3. pointerup後にDense Keysを生成
4. 全結果を検証
5. 一回のmutationでcommit
6. 一回のTimeline Historyとして確定

### 12.3 `system/history.js`変更を前提にしない

既存Timeline Motionが専用snapshot/history経路を持つ場合、それを再利用する。

CODEXは次を確認する。

- Clip Motion gestureがHistoryをどこで開始・確定するか
- before/after snapshotの単位
- Timeline mutation API
- History適用時のpreview refresh
- redo時のkey validation
- Project historyとTimeline historyの境界

既存契約で表現できる場合、`system/history.js`へ新しいcommand系統を追加しない。

## 13. EventBusと更新通知

新規EventBusイベントの追加を前提にしない。

CODEXは次を調査する。

- transform key更新後の既存通知
- Timeline UI再描画の入口
- preview compositorのinvalidate入口
- playback停止・再開通知
- selection変更通知
- Project dirty通知
- save状態更新
- toast表示契約

既存mutation入口が必要な通知を発火する場合、Perform固有イベントは追加しない。

新規イベントが必要な場合も、UI内部のcapture状態とProjectデータ更新を混在させない。

## 16. 性能とメモリ

### 16.1 Raw Sample上限

長時間pointerを保持した場合に、固定時計sampleが無制限に増えないよう上限または圧縮が必要である。

候補:

- capture最大時間
- 最大sample数
- 一定間隔sample
- 同一位置sampleのrun-length表現
- coalesced sampleの過剰保持抑制

ただし、Hold区間を失わないことが条件である。

### 16.2 Dense Keys

長いClipで全Frame複合キーを生成すると、保存容量、Timeline描画、History snapshot、copy/pasteへ影響する。

CODEXは次を計測する。

- 24 / 48 / 120 / 240 / 1000 Frame
- key生成時間
- History snapshot容量
- save JSON増加量
- Timeline marker描画負荷
- playback sampling負荷
- Undo/Redo時間
- copy/paste時間

性能上限が問題になる場合も、正しさを崩す簡略化を先行導入しない。

## 19. 受け入れ条件

### 19.1 入力・時間

- 同じRaw軌跡と時刻列ならデバイスHzに関係なく同じ結果になる
- pointerが静止中でもHold時間が記録される
- 先頭Frameが`r=0`
- 最終Frameが`r=1`
- 単Frame Clipでは無効理由を表示する
- `T_total=0`で例外を出さない
- pointercancel、Escape、blurでProject変更を残さない

### 19.2 座標

- pointerdown時にClipがジャンプしない
- Camera zoom・pan中も同じworld移動になる
- anchor位置による差異を正しく扱う
- popup previewと通常Canvasで座標契約が一致する
- screen座標をMotion値へ直接保存しない

### 19.3 Motion

- 位置以外のparameterを意図せず変更しない
- 複合キーBakeの場合、各整数Frameの対象外parameter表示を維持する
- 暗黙始点・終点を壊さない
- HOLD / Easing消失の可能性を事前表示する
- LINEAR出力で予期しないovershootを発生させない
- Clip retiming後も壊れない
- copy/paste後も壊れない

### 19.4 History・保存

- 1 Perform = 1 Undo
- Redoで同じ結果へ戻る
- save/load後にFrame値が一致する
- Raw SampleをProjectへ保存しない
- runtime overlay stateを保存しない
- Project切替後にcapture stateが残らない

### 19.5 描画経路

- Animation Table previewと通常再生が一致する
- onion表示が同じMotion sampler結果を使う
- export結果がCanvas playbackと一致する
- 旧Projectで結果が変わらない
- Perform未使用Projectは従来経路を維持する

### 19.6 性能

- 長時間captureでRaw Sampleが無制限に増えない
- Dense KeysがTimelineを実用不能にしない
- History snapshotが上限なく増えない
- cancel後にrAF、event listener、overlayが残らない
- Project削除・Clip削除後に参照が残らない

## 20. 停止・再設計条件

次のいずれかが確認された場合、CODEXは実装を進めず、Phase 7計画を再設計する。

- 現行Motion schemaでは対象外parameterを維持して位置だけ変更できない
- Dense Composite-Key Bakeが既存Clip Motionを不可逆に破壊する
- preview、playback、onion、exportで異なるsamplerを使い、短期統合が不可能
- screen→world変換を再利用できず、座標系の二重実装が必要になる
- Timeline Historyへ一操作として安全にcommitできない
- 長いClipでDense Keysが保存・再生上の重大問題を起こす
- pointer固定時計captureが既存描画入力と競合する
- Perform modeの排他が既存UI契約を大きく破壊する
- Easing消失をユーザーへ適切に説明・復元できない
- 旧Project互換性を維持できない

停止判定は機能廃止を意味しない。必要に応じて、次の代替案を検討する。

- Perform専用の非破壊position track
- Motion parameter別track化
- Raw Perform Takeを別データとして保持し、再生時に評価
- 位置Motionだけを持つModifier層
- Motion Graph側の構造拡張後に再開

これらは現行アーキテクチャへの影響が大きいため、Phase 7の即時実装案には含めない。

## 21. 技術評価まとめ

| 項目 | 判定 | 理由 |
|---|---|---|
| 機能コンセプト | 採用候補 | 位置演技を直感入力できる |
| 相対時間方式 | 条件付き採用 | 全体時間から解放されるが局所速度差は残る |
| PointerEventのみの記録 | 不採用 | 中間Holdを復元できない |
| Pointer＋固定時計 | 採用候補 | 静止時間を記録できる |
| Sample→Frame丸め | 不採用 | イベントHz依存と終端偏重 |
| Frame時刻→軌跡評価 | 採用候補 | 全Frameへ安定して値を生成できる |
| `round(r * frameCount)` | 不採用 | 最終Frame側へ偏る |
| `k / (frameCount - 1)` | 採用候補 | 先頭・終端を正確に対応 |
| X/Y独立RDP | 不採用 | 複合キー・共通Easingと衝突 |
| 時間付きXY誤差簡略化 | 後続候補 | 共通Frame集合を維持できる |
| Dense Keys | MVP候補 | 正しさを確認しやすい |
| Bezier自動フィット | 後続研究 | 現行linked easingと衝突し得る |
| `history.js`新規拡張 | 調査後判断 | 既存Timeline History再利用を優先 |
| 新規EventBusイベント | 調査後判断 | 既存mutation通知を優先 |
| Hold Heat Map | UI後続Slice | コア成立後に追加 |
| Clip自動拡張 | MVP不採用 | Clip全長fitでは不要 |

## 22. 最終提案

モーションパフォームは、Phase 7候補として維持する。

ただしPhase 7の最初の目標は、次の一文で表現できる範囲に限定する。

> 選択Clipをキャンバス上で一度ドラッグし、その相対時間付き位置軌跡を、既存Motion samplerとHistory契約を壊さず、Clip全長のLINEARな位置キーとして記録する。

Phase 7で優先する順序は次とする。

1. 実コード監査
2. pointer＋固定時計によるHold記録
3. 既存座標変換の再利用
4. Frame時刻からの軌跡resampling
5. 複合キー整合とDense Bake
6. 一操作一History
7. preview/playback/onion/export一致
8. UI仕上げ
9. 性能評価
10. 必要な場合のみ簡略化

Bezier自動フィット、parameter別Easing、BONE Part Performなどは、基本契約が安定した後の独立した研究・実装計画へ送る。
