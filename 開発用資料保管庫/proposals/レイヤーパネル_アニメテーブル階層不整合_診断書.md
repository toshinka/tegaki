## 0. 結論（先に要点）

ご指摘の3点はいずれも**実際にコード上で確認できる、既知の構造的な原因**によるものです。単発の描画バグではなく、**「LayerSystemの実データ（実行）」と「Lane/Animation Table側の同期スナップショット（見た目）」が別々の仕組みで管理されており、両者を同期させる処理がAnimation Table非表示中は完全に停止する**という設計に起因します。`PHASE4Z_BOUNDARY.md`はこの部分を最初から「暫定橋渡し」と明記しており、`PROGRESS.md`にも同種の症状が「限定修正」止まりとして記録されています。つまり**既知の未解決領域に、まさに今回ご指摘の症状が該当する**、というのが調査結果です。

主原因は次の4つです（重要度順）。

1. **Animation Table非表示中はLaneの同期処理が完全に止まる**（最重要・確定）
2. **初回同期以降、新規作成したレイヤーにはLaneが自動的に付かない**（確定）
3. **同期のたびにLane順序を全再構築するため、非表示中の変更が復帰時に「まとめてジャンプ」して見える**（確定）
4. **LaneモデルはFolderという概念を持たず、Layer Panelのフォルダ入れ子表示と構造的に噛み合わない**（確定・設計上の既知の制約）

---

## 1. 原因1: Animation Table非表示中は同期が完全停止する（最重要）

`animation-table-popup.js`のLane同期は、パネルの`render()`内でのみ呼ばれています。

```js
render() {
    if (!this.panel || !this.isVisible) return;   // ← 非表示なら即return
    ...
    const layers = this.layerSystem?.getLayers() || [];
    const activeIndex = this.layerSystem?.getActiveLayerIndex() || 0;
    this.model.syncWithLayers(layers, activeIndex);   // ← Lane同期の唯一の入口
    ...
}
```

さらに、レイヤー追加・削除・並べ替えなどのイベントを受けて呼ばれる`requestUpdate()`自体が、非表示時には`render()`をスケジュールしません。

```js
requestUpdate() {
    if (!this.isVisible) {
        this._scheduleLaneReferencePreviewUpdate();   // サムネイル更新のみ、Lane同期は行わない
        return;
    }
    ...
    this._updateTimeout = setTimeout(() => { this.render(); }, 32);
}
```

`syncWithLayers`の呼び出し箇所はコードベース全体でこの1箇所のみです。つまり、**Animation Tableを閉じている間にレイヤー・フォルダを追加/削除/並べ替えても、Lane側のデータは一切更新されません。** 開いた瞬間にまとめて再構築されるため、「展開している時／していない時で挙動が違う」という体感は正確な観察です。

---

## 2. 原因2: 初回同期以降、新規レイヤーにはLaneが付与されない

`syncWithLayers()`（`animation-data-model.js`）には、初回だけ有効になるフラグがあります。

```js
const allowInitialLayerImport = !this.layerSyncInitialized && this.tracks.length === 0;
```

`layerSyncInitialized`は一度trueになると戻りません。新規レイヤーが見つかった場合の分岐は次の通りです。

```js
} else {
    if (!allowInitialLayerImport) return null;   // 初回以降は新規Laneを作らない
    return new LaneModel({ ... });
}
```

つまり、**「CAFがまだ存在しない標準時」に最初に開いたタイミングでのみ自動でLaneが作られ、それ以降にアニメ作業をしながら新しく描き足したレイヤーは、Animation Tableに自動的には反映されません。** これは意図的な移行措置（`PHASE4Z_BOUNDARY.md`「最終仕様では、通常Layerそのものではなく、ClipInstanceを置く行になる」）ですが、ユーザー体感としては「レイヤーを増やしたのにアニメテーブル側に出てこない/挙動が読めない」という形で現れます。標準時とTable使用中で挙動が変わる、というご指摘の2点目と一致します。

---

## 3. 原因3: 同期のたびにLane順序を全再構築する

`syncWithLayers()`の末尾で、Lane配列はその都度ゼロから組み直されます。

```js
this.tracks = [...newTracks, ...missingSourceLanes, ...retainedUnlinkedLanes];
this.tracks.forEach((lane, index) => { lane.orderIndex = index; });
```

`newTracks`の順序は、その時点の`layerSystem.getLayers()`（＝LayerPanelの現在順序を反転したもの）に**そのまま**従います。原因1により、Table非表示中に行ったレイヤー並べ替え・フォルダ移動は同期されずに溜まり、次にTableを開いた瞬間にこの全再構築が走るため、**それまで見えていたLane順序から急に飛んだように変わる**ことになります。`PROGRESS.md`の既知残存に記録されている次の記述は、この現象そのものです。

> 通常modeでLayer Panel選択とV変形Rasterが食い違う例、**Table表示有無でFolder/Layer card順が揺れる例**はPhase 6rで限定修正した。

「限定修正」であり、今回コードを確認した限り、非表示時に同期を止める`if (!this.isVisible) return;`のガード自体は現在も残っています。つまりこの症状は**未解決のまま残っている既知課題**です。

---

## 4. 原因4: LaneはFolderという概念を持たない

`syncWithLayers()`の`newTracks`生成処理では、フォルダは明示的に除外されています。

```js
if (layerData.isFolder) return null;
```

一方、Layer Panel側のフォルダ入れ子表示は、LayerSystem内の**別の並行データ構造**（`layerData.parentId` / `layerData.children[]`）で管理されており、実際の合成順序を決める`currentFrameContainer.children`（フラットなPIXI Containerの子リスト、`getLayers()`が返すもの）とは別物です。この2つを一致させる処理（`_finalizeLayerReorder` / `_compactFolderChildren`）はLayerSystem内の通常のレイヤー操作に対しては比較的丁寧に実装されていますが、**Animation Table側のLane一覧は、そのフラットな`getLayers()`の並びをそのまま使うだけで、どのフォルダに属しているかという情報を一切持ちません。**

結果として、Layer Panelでは「フォルダA配下にレイヤー1・2」という入れ子表示になっている一方、Animation Tableでは同じレイヤーがフォルダの概念なしに**フラットな1本のLane列**として、かつ原因1・3の影響で古い/飛んだ順序で表示されるという、構造的な二重管理状態になっています。`PHASE4Z_BOUNDARY.md`が明記する通り、これは意図的な移行途中の状態です。

> `Lane = LayerSystemの通常Layer由来`の同期。`syncWithLayers()`によるLane生成。... これらは移行用の暫定足場であり、最終仕様として固定しない。

---

## 5. 付随所見: 使われていない並行実装（将来のバグ温床）

`layer-system.js`には、フォルダへレイヤーを追加する処理が**2種類**存在します。

- `moveLayerIntoFolder()` / `_applyMoveLayerIntoFolder()`: `parentId`更新に加えて、フラット順序も`_moveLayerObjectToIndex` + `_compactFolderChildren`で正しく再配置する。**現在Layer Panelのドラッグ&ドロップから使われているのはこちら。**
- `addLayerToFolder()`: `parentId`とデータ上の`children[]`だけを更新し、**フラット順序（`currentFrameContainer.children`）は一切動かさない。**

調査の範囲では`addLayerToFolder()`の呼び出し箇所は見つからず、現状は未使用（デッドコード）と見られます。ただし、これが将来どこかから呼ばれる、あるいは似た実装が新規コードでコピーされた場合、**parentId上は「フォルダの中」なのに実行順序上は「フォルダの外」という、まさに今回ご指摘の食い違いを新たに生む**危険な実装です。削除するか、少なくとも呼び出し禁止をコメントで明示することを推奨します。

## 6. 「重複表示」についての仮説（要追加検証）

`layer-panel-renderer.js`には、通常のレイヤー行（`legacy-layer-card`）とは別に、選択中CAFの内部Layerを表示する**「CAF内部Layerミラー」行（`clip-layer-mirror`）**という別レンダリング経路が存在します（`PHASE4Z_BOUNDARY.md`が言う「選択ClipAssetの内部Layerミラー表示」に相当）。

これは仕様上意図された別表示ですが、名前やサムネイルが元のレイヤーと酷似するため、**ある1枚のレイヤーが「通常レイヤー行」としても「選択中CAFの内部Layerミラー行」としても同時に見えている状況**は、ユーザー視点では「同じレイヤーが2箇所に重複している」ように映る可能性があります。これは今回のコード調査だけでは断定できず、実際にどのタイミングで両方が同時表示されるかをBrowser上で再現確認する必要があります（7章の追加調査候補に記載）。

## 7. 症状 対 原因 対応表

| ご指摘の症状 | 該当する原因 |
|---|---|

## 8. 推奨アクション

`PHASE4Z_BOUNDARY.md`の「Codexが担当すべき作業」に`syncWithLayers()`の根本変更・Laneモデルの責務整理が明記されている通り、これはGeminiが独断で直すべき範囲を超えています。次の順で進めることを推奨します。

1. **応急処置（Codex承認の上でGemini実装可能な範囲）**: Table非表示中もイベント受信時に**軽量な差分同期**（少なくとも`layer:created` / `layer:deleted` / `layer:reordered` のIDセット差分だけ）を`this.model`へ反映し、表示中と同じ全再構築を毎回行わない設計にする。表示再開時の「まとめてジャンプ」を防ぐ第一歩になる。
2. **本格対応（Codex設計必須）**: `PHASE4Z_BOUNDARY.md`が既に示す方向性の通り、`Lane`を`LayerSystem`の通常レイヤーから独立させ、`syncWithLayers()`依存を段階的に外す。次の安全な進め方として文書内にも明記されている「`syncWithLayers()`と`sourceLayerId`依存の棚卸し」から着手する。
3. **デッドコード整理**: 未使用の`addLayerToFolder()`を削除、または呼び出し禁止コメントを付す。
4. **要追加検証**: 6章の「CAF内部Layerミラーと通常レイヤー行の重複表示」について、実際にCAFを開いた状態でLayer Panelを目視確認し、重複が実在するか、条件を再現できるかを確認する。
