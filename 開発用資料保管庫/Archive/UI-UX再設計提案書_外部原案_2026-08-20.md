# UI/UX再設計提案書
## ―「思考の水位」を揃える、モダン描画・アニメーションUIへの段階的移行―

### 1. 提案の目的

現在のWEBお絵かきツールは、描画機能、独自ショートカット、アニメーションテーブル、Q/Vを含む独自操作系など、機能面の蓄積が進んでいる。

一方、機能実装を優先してきた結果、特にアニメーション周辺では、各機能の配置・見た目・パネル構造について再整理できる余地が大きい。

今回の再設計では、Callipeg Studio、CLIP STUDIO PAINTのシンプルモード、Adobe Frescoなどに見られる現代的なタッチ対応描画UIを参考にしつつ、既存ツールをそれらの模倣品へ変更することは目的としない。

目的は以下の3点とする。

1. UI全体の視覚言語を現代化する。
2. Callipeg等との併用時に発生する認知・学習コストを下げる。
3. 現在の独自操作哲学と将来のアニメーション・物理演算・AI機能を収容できるUI骨格を作る。

---

# 2. 中核思想：「思考の水位」を揃える

本リデザインで重視するのは、単純な外観上の類似ではなく「思考の水位」である。

異なるアプリ間を行き来するとき、ユーザーは毎回、

- ツールはどこにあるか
- 再生はどこか
- これはボタンかパネルか
- どこを押せば展開するか
- タイムラインはどう読むか
- 現在何が選択されているか

といった低レベルのUI解釈を要求される。

この処理が増えるほど、本来集中したい、

- 描く
- 動きを考える
- タイミングを見る
- ポーズを修正する
- 物理挙動を調整する

といった制作上の思考が中断される。

そこで、Callipeg等と機能が異なる場合でも、

「似た役割のものが、似た視覚文法と空間文法で存在する」

状態を作る。

これを「思考の水位を揃える」と定義する。

完全なUI互換を目指すのではない。

目標は、

> アプリを切り替えても、基本操作を探すために思考の水位を下げなくて済むこと。

である。

---

# 3. 模倣するのは「製品」ではなく「視覚文法」

Callipegの個々のSVGやUIをそのまま複製することは目的としない。

参考にするのは、以下のようなデザイン上の文法である。

- 縦長ツールバーの上下端を大きく丸めたカプセル状コンテナ
- パネルとキャンバスを明度差で分離する構成
- シンプルな単色SVGアイコン
- 選択状態のみをアクセント色で明確化
- 非選択アイコンの視覚的主張を弱くする
- ボタン、スライダー、トグル等の高さ・角丸・余白の統一
- 数値より直接操作を優先する
- キャンバスを最優先し、常時表示するUIを限定する
- 状況に応じて必要なコントロールだけを見せる

したがって、

「Callipegと同じSVGを描く」

のではなく、

「同程度の情報密度、線幅、余白、コントラストを持つ独自SVGを作る」

ことを目標とする。

---

# 4. 第一段階：機能を変更せず、視覚デザインのみ刷新する

最初のリデザインでは、既存機能の挙動変更を原則として行わない。

対象は主に以下とする。

- SVGアイコン
- ボタン
- トグルスイッチ
- スライダー
- パネル背景
- パネル境界
- 選択表示
- ホバー表示
- disabled表示
- 数値入力欄
- スクロールバー
- タイムラインセル
- 余白
- 角丸
- アイコンサイズ
- アイコン線幅

機能変更とUI変更を分離することで、不具合発生時の原因を限定する。

---

# 5. デザイントークン化

色や形状を各コンポーネントへ直接記述せず、共通デザイントークンへ集約する。

例：

```text
surface.canvas
surface.panel
surface.panelRaised
surface.popup

border.subtle
border.active

text.primary
text.secondary
text.disabled

icon.normal
icon.active
icon.disabled

control.hover
control.pressed
control.active

accent.primary

timeline.cell
timeline.active
timeline.selected

onion.previous
onion.next
```

角丸についても、

```text
radius.small
radius.control
radius.panel
radius.capsule
```

などに統一する。

これによって、将来Callipeg寄りから独自テーマへ変更する場合でもUI構造を書き換える必要をなくす。

---

# 6. 左サイドバー

左サイドバーは現在のツール構成を基本的に維持する。

外観については、添付したCLIP STUDIO PAINTシンプルモードやCallipegのような、

- 細身
- 上下端が丸い
- 背景とアイコンのコントラストが明確
- アクティブ状態だけ強く発色
- アイコン周辺に過度な枠を作らない

という方向へ寄せる。

ただしツールの意味、順番、独自機能まで他アプリに合わせる必要はない。

---

# 7. Q / Vを「移動可能な操作装置」とする

Q/Vは本ツール独自の強みとして維持・発展させる。

左サイドバー上に存在するQ/Vをドラッグ可能とし、

- 左ツールバー上
- 右ツールバー上
- 必要に応じた別の固定ポイント

へ移動できるようにすることを検討する。

目的は単なるレイアウトカスタマイズではない。

例えば右利きユーザーが右側へパネルを配置した場合でも、Q/Vによる高速切り替えを手やペンの近くへ移動できる。

この機能は、

「ユーザーにUI全体を自由配置させる」

のではなく、

「使用頻度の高い操作だけを身体側へ移動できる」

という設計とする。

フルカスタマイズ型UIより認知負荷が低く、同時に個人差へ対応できる。

---

# 8. フローティングツールパネルは維持する

QTP等の自由に移動・開閉できるツールパネルは、本ツールのストロングポイントとして維持する。

Callipeg等へ合わせるために固定パネルへ統合しない。

ただし外観上のデザイン哲学は共通化する。

つまり、

- 固定UI
- フローティングUI
- ポップアップUI

で機能や配置思想は異なっても、

- 角丸
- 配色
- アイコン線
- 選択表現
- スライダー
- トグル
- 余白

については同じデザインシステムを使用する。

これにより「違う種類の装置だが、同じアプリに属している」という視覚的一貫性を作る。

---

# 9. 右上にクイック操作テーブルを追加する

現在ショートカット中心になっている一部操作は、UI全体が安定した段階で右上のクイックテーブルとして追加する。

候補：

- Undo
- Redo
- 左右反転
- 上下反転
- キャンバス回転
- 回転リセット
- 表示位置リセット
- 必要に応じて100%表示
- その他高頻度表示操作

CLIP STUDIO PAINTシンプルモードのように、キャンバスを邪魔しない小型の操作領域を想定する。

ただしすべてを入れる必要はない。

ショートカットで高速に扱える操作と、画面上に常駐させる価値のある操作を分け、実使用を見ながら削減する。

原則：

> UI追加は「機能が存在するから」ではなく、「視認可能であること自体に価値があるか」で判断する。

---

# 10. アニメーションUIは配置から再設計する

アニメーションテーブル周辺は、既存機能の実装を優先して作られてきたため、今回の主要リデザイン対象とする。

機能そのものを捨てるのではなく、配置と視覚構造を作り直す。

Callipeg等を参考に、時間操作に関するUIをひとまとまりとして認識できるようにする。

特に再生操作については、

> 再生ボタンをアニメーションUI中央付近へ配置する。

ことを基本案とする。

再生はアニメーション作業における中心操作であり、端へ寄せるより視認性と意味上の中心性を優先する。

---

# 11. アニメーション操作は二段構成を許容する

本ツールは独自アニメーション機能を増やしていく予定であり、Callipegと同じ一段構成へ無理に収めない。

必要であれば二段構成を正式な設計とする。

例：

```text
[セル操作 / Onion / Mode / その他]

        [前][再生][次]
[先頭][末尾][Loop][Flip][その他]
```

重要なのは一段か二段かではなく、

- 再生系
- セル操作系
- 表示補助系
- モード系

の意味的なまとまりが視覚的にも認識できること。

---

# 12. タイムライン／アニメテーブルを「ドック型」へ変更する

現在の自由配置中心のアニメーションテーブルについては、より安定した固定式ドックへ寄せる。

ただしサイズは可変とする。

最低限、以下の状態を想定する。

### 下ドック

```text
┌─────────────────────────┐
│                         │
│         Canvas          │
│                         │
├─────────────────────────┤
│    Animation / Timeline │
└─────────────────────────┘
```

### 右ドック

```text
┌─────────────────┬────────┐
│                 │        │
│     Canvas      │Timeline│
│                 │        │
└─────────────────┴────────┘
```

### 左ドック

必要であれば左右反転も可能にする。

### 収納

アニメーションを使用しない場合は閉じてキャンバスを最大化する。

---

# 13. 「完全自由配置」ではなく「制約された可変性」

すべてのパネルを好きな場所へ置けるUIは、一見柔軟だが、

- レイアウト崩壊
- 保存処理
- ウィンドウサイズ変更
- パネル重複
- キャンバス遮蔽
- モバイル対応
- UI状態の再現

などの複雑さを増大させる。

そこでアニメーションテーブルについては、

「自由に動かせる」

ではなく、

「左・右・下という意味のある場所へドックでき、幅または高さだけ変更できる」

構造を基本とする。

これは自由度を減らすためではなく、UIの予測可能性を上げるためである。

---

# 14. 既存の高速操作は「不変条件」とする

UIをCallipeg等に近づけても、本ツール固有の高速操作を失ってはならない。

特に既存の、

- マウスホイールによる拡大縮小
- ホイールによるフレーム送り
- タイムライン上の高速操作
- キーボードショートカット
- Q/V操作
- 独自ジェスチャ

は、原則として維持する。

CodexによるUI改修では、これらを見た目に合わせて変更・削除してはならない。

これを実装上の明確な不変条件とする。

> Visual redesign must not alter existing gesture, wheel, keyboard, Q/V or timeline interaction behavior unless explicitly requested.

---

# 15. 「見える操作」と「高速操作」の二層構造

UI上にボタンを置くこととショートカットを維持することは競合しない。

初心者：

```text
画面上のボタンを見る
↓
意味を理解する
↓
操作する
```

熟練者：

```text
ショートカット / Wheel / QV
↓
即操作
```

という二層構造を意図する。

画面上のUIは説明書でもあり、ショートカットは高速道路である。

熟練者のためにUIを消し過ぎず、初心者のために高速操作を捨てない。

---

# 16. Onion Skinの視認性を改善する

オニオンスキンは単に機能を追加するだけでなく、Callipeg等を参考に視認性そのものを再評価する。

特に、

- 過去フレーム
- 現在フレーム
- 未来フレーム

を瞬間的に区別できることを重視する。

色はCallipegの傾向を参考にしてよいが、固定RGB値のコピーは行わず、独自の色として再設計する。

構造としては、

```text
Previous 3
Previous 2
Previous 1
Current
Next 1
Next 2
Next 3
```

の距離に応じ、

- 色相
- opacity
- 表示枚数

を管理可能にする。

デフォルト値は見やすさを優先し、上級者向けには設定変更可能とする。

---

# 17. タイムラインの「動かし方」も認知互換の対象とする

思考の水位を揃える対象は静的なレイアウトだけではない。

- セルを選択する
- ドラッグする
- 長さを変更する
- 再生位置を移動する
- フレームを送る
- タイムラインを拡大縮小する

といった時間操作についても、一般的なアニメーションソフトで期待される操作と大きく矛盾しない形を目指す。

ただし既存の便利な操作が一般的ソフトより高速である場合は、そちらを維持する。

目標は完全互換ではなく、

「最初の数秒で意味が推測できること」

とする。

---

# 18. 将来のGraph Editorを前提にレイアウトを設計する

物理演算、通常キーフレーム、イージングを扱う場合、最終的には値をグラフとして確認できることが望ましい。

将来的には、

```text
Position X
Position Y
Rotation
Scale
Opacity

Physics influence
Spring
Damping
その他パラメータ
```

を、

```text
time → value
```

として共通のGraph Editorへ表示できる構造を目指す。

これにより、

- 手動キーフレーム
- Bézier easing
- 物理演算結果
- 手動補正

を同一の時間軸上で理解できる。

したがって今回のアニメーションパネル再設計では、将来的にTimelineとGraphを切り替え、または分割表示できる余地を残す。

---

# 19. Motion Path / Guide Rail

アニメーション機能として、オブジェクトや身体部位の移動軌道をキャンバス上で可視化・編集する機能を将来的に導入する。

例：

```text
● Start
 ╲
  ╲
   ╰──────● End
```

ベジェ曲線等で軌道を指定し、

```text
position = path(t)
```

として時間に沿って移動させる。

初期段階では、

- 軌道表示
- 制御点編集
- 始点・終点
- 軌道上の現在位置
- イージング

程度から開始する。

その後、

- 腕などの関節追従
- IK
- 物理遅延
- 軌道への吸着
- AIによる軌道候補

へ発展可能とする。

これはCallipeg由来の単独機能としてではなく、本ツールで以前から構想している変形・物理・アニメーション支援を視覚化するための共通UIと位置付ける。

---

# 20. UIの類似は「二刀流」のための投資とする

Callipeg Studioは、自作ツールを置き換える競合としてのみ見る必要はない。

Callipegが成熟した段階で導入し、

- 自作WEBツール
- Callipeg Studio

を用途に応じて併用することを前提としてもよい。

その場合、自作ツール側の視覚文法を一定程度Callipegへ近づけておけば、

```text
WEBツール
   ⇅
Callipeg
```

を移動した際の認知コストが下がる。

これはファイル互換とは別種の、

「認知上の互換性」

である。

したがってUIの類似性自体にも実用的な意味を持たせる。

---

# 21. ただし「Callipegクローン」にはしない

以下については、本ツール固有の哲学を優先する。

- Q/V
- QTP
- マウスホイール操作
- ショートカット
- 二段アニメーション操作列
- WEB用途
- 将来のAI統合
- 将来の物理演算
- 将来の変形・リギング
- 独自投稿フロー
- 独自の描画補助

Callipegと異なること自体を問題としない。

共有するのは「入口」であり、「到達可能な機能範囲」ではない。

# 22. UX設計原則

今後UIを追加する際は、以下を判断基準とする。

### A. Canvas First

制作物そのものを最大表示する。

### B. Recognition Before Recall

ショートカットを知らなくても、重要操作は画面を見れば推測できる。

### C. Expert Shortcuts Remain

初心者向けUI追加によって熟練操作を削除しない。

### D. Constrained Flexibility

無制限な自由配置ではなく、有用な範囲だけカスタマイズ可能にする。

### E. Contextual Controls

現在の操作と無関係なコントロールを常時見せない。

### F. Stable Spatial Memory

同じ意味の操作は基本的に同じ位置に存在する。

### G. Cross-App Cognitive Compatibility

一般的な描画・アニメーションアプリとの間で、基本操作の視覚文法を必要以上に乖離させない。

### H. Preserve Unique Advantages

一般的でないこと自体が高速性や使いやすさにつながる場合は独自仕様を優先する。

対象：

- SVG

- Slider
- Button
- Color
- Radius
- Spacing
- Hover
- Active
- Disabled
- Panel
- Tooltip

この段階ではアプリ構造を変更しない。

---

## Phase 2 — Static Layout Redesign

主に配置を変更する。

- 左サイドバー再デザイン
- 右上クイックテーブル用領域
- アニメーション操作列再配置
- 中央Playback
- 二段表示
- Animation Dock
- 左右／下配置

- Onion Skin改善
- Timeline selection改善
- exposure操作

## Phase 4 — Advanced Animation UI

---

# 24. Codex実装時の重要な禁止事項

Codex側では、UI改善を理由として以下を勝手に変更しない。

- 既存ショートカット
- Wheel挙動
- Pointer操作
- Q/V挙動
- QTP機構
- 描画エンジン
- フレームデータ
- 保存形式
- アニメーションロジック
- ツールの機能的意味

必要な変更がある場合は、UIリファクタリングとは別Issueとして扱う。

---

# 25. UIコンポーネントとアプリ機能を分離する

今後の保守性のため、

```text
Toggle
Slider
IconButton
ToolButton
Panel
Dock
Toolbar
Splitter
Popup
TimelineButton
```

等は共通UIコンポーネント化する。

例えばBrush Size SliderとOnion Opacity Sliderで別々のCSSを作らず、同じSliderコンポーネントを使用する。

これが今回のモダン化で最も重要な技術的成果の一つになる。

見た目を整えるだけで終わらせず、

「今後UIを追加しても自動的に同じデザインになる」

状態を作る。

---

# 26. 初期実装における優先順位

最初から全体を変更しない。

推奨順：

```text
1. Design Tokens
       ↓
2. SVG icon system
       ↓
3. Button / Toggle / Slider
       ↓
4. 左サイドバー
       ↓
5. Animation controls
       ↓
6. Animation Dock
       ↓
7. 右上Quick Table
       ↓
8. Onion Skin
       ↓
9. Timeline UX
```

各段階で既存操作が維持されていることを確認してから次へ進む。

# 27. 成功条件

今回のリデザインは「Callipegに似たかどうか」だけでは評価しない。

以下を満たせば成功とする。

- 初見でも主要ツールの場所を推測しやすい
- 描画領域を過剰に圧迫しない
- アニメーション再生操作がすぐ見つかる
- 過去／未来Onion Skinを瞬時に区別できる
- Callipeg等から移動しても基本操作で迷いにくい
- 既存ユーザーのWheel・shortcut・Q/V操作を損なわない
- QTPなど独自機能が維持される
- 左右／下のAnimation Dockが自然に使用できる
- UI追加時にデザインがばらつかない
- 将来Graph Editorを追加できる
- 将来Physics UIを追加できる
- 将来AI支援を追加できる

# 28. 最終方針

本ツールはCallipeg、CLIP STUDIO PAINT、Frescoを模倣するのではない。

それらが長いUX設計の結果として獲得した、

「ユーザーが余計なことを考えず制作へ戻れる視覚言語」

を参考にする。

共通化すべきなのは、

```text
見た瞬間に意味が分かる部分
```

であり、

独自化すべきなのは、

```text
制作速度や表現能力を高める部分
```

である。

その境界を「思考の水位」で判断する。

慣習的なUIを独自化することでユーザーに利益がないなら、既存の視覚文法へ寄せる。

一方、Q/V、QTP、Wheel操作、将来のPhysics・AI・Transformなど、独自化によって制作体験が向上する部分については積極的に独自設計を行う。

目標は、

> 「見たことがあるので迷わない。しかし使い込むと、このツールにしかない速度と能力がある」

というUIである。
