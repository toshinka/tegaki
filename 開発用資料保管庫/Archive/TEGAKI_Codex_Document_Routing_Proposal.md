# TEGAKI ドキュメント・ルーティング最適化提案

> Tegaki採否（2026-08-26）: `開発用資料保管庫/proposals/00_計画索引.md`が既に文書の役割・読む場面・現行 / Archive境界を提供し、`AGENTS.md`と`PROGRESS.md`が標準読順を固定しているため、新しいrouting層は追加しない。Status / Area / Read whenの一括tag化も行わず、将来不足が出た文書だけ既存索引の表へ追加する。本書は有効な監査観点を残す外部提案としてArchiveへ保管する。

## 目的

TEGAKI プロジェクトでは、過去の提案・未実装案・現在の実装計画・長期的な設計情報が並行して存在する。

これは単純な重複ではなく、以下のような開発特性を支えるために必要な情報である。

- 以前の提案を、後の実装段階で再評価することがある
- 未実装の提案へ追加案を継ぎ足すことがある
- 複数の提案が、後になって統合されることがある
- 現在のコード状態によって、過去案の採否や実装方法が変わる
- 提案書は実装命令ではなく、将来参照する設計知識として残す価値がある

そのため、本提案ではドキュメント量を強く削減したり、古い提案を整理・統合しすぎたりしない。

改善対象は **情報量そのものではなく、Codex が「今回どの情報を読むべきか」を判断するためのルーティングコスト** とする。

---

## 基本方針

### 1. 情報は捨てない

古い proposal、未実装案、設計上の検討履歴は、将来の再評価に利用できるため原則として残す。

過去案であることだけを理由に削除・統合・要約しない。

### 2. 通常経路から外す

すべての proposal や過去文書を毎回読む必要はない。

Codex が現在のタスクに関連する文書だけを選択できるよう、軽量な索引またはメタデータを利用する。

### 3. 現在の構造を優先する

既に TEGAKI 内で同等の仕組みが存在する場合、新しい管理方式を追加しない。

まず現在の `AGENTS.md`、進捗文書、Phase 文書、proposal 群、設計文書、Archive、既存の索引類を調査し、既存構造で十分なら変更不要と判断する。

### 4. 最適化そのものを目的化しない

ドキュメント整理のために新しい維持作業を大量に発生させない。

今回の改善によって人間側の管理負荷が増える場合は採用しない、または縮小する。

---

## 想定する情報の役割

現在の構成を調査した上で、概念的には以下の役割分離が維持されていることが望ましい。

| 種別 | 主な役割 |
|---|---|
| AGENTS 系 | Codex の恒久的な行動規則、読書順、変更時の原則 |
| Architecture / TEGAKI 系 | 現在有効な構造、長期設計、主要な技術方針 |
| Progress / Current 系 | 現在地、直近の進捗、残件 |
| Phase | 今回実装する範囲、採用済み判断、検証条件 |
| Proposal | 将来候補、未採用案、設計知識、検討材料 |
| Archive | 完了済み Phase、過去の実装履歴 |

ファイル名や配置は既存構造を優先し、この表へ合わせるためだけのリネームや移動は行わない。

---

## 問題設定

現在の TEGAKI では、情報を単純に削減すると以下の問題が発生する可能性がある。

### 過去提案の再発見性低下

未実装だった提案が、後の機能追加によって実現可能になる場合がある。

強い整理や統合によって元提案が失われると、設計上の選択肢そのものが消える。

### 現在仕様と将来案の混同

proposal を現在仕様へ統合しすぎると、未採用案が現行仕様のように扱われる危険がある。

逆に proposal を完全に隔離すると、関連機能を実装する際に Codex が存在を発見できない。

### ドキュメント税

関連性の低い大量の文書を毎回読ませると、コンテキスト・トークン・探索時間を消費する。

問題は文書が存在することではなく、**必要性を判断する前に全文を読む必要があること** にある。

---

# 提案: Proposal Routing Layer

## 概要

既存の proposal 本文は原則変更せず、その手前に軽量な「ルーティング層」を置く。

ルーティング層は proposal の内容を再説明する場所ではない。

目的は Codex が以下を低コストで判断することである。

1. この proposal は現在のタスクに関係するか
2. 現在有効なのか、未採用なのか、置き換え済みなのか
3. どのタイミングで読むべきか
4. 他の proposal や実装との関係は何か

---

## 推奨メタデータ

既存の計画索引・proposal index・実装予定一覧などがある場合、そこへ必要最小限の項目だけ追加する。

例:

```md
### 自動メッシュ / 自由コントロールポイント

Status: PROPOSED
Area: Mesh, Bone, Stroke
Implementation: NOT_STARTED
Depends: Bone 基盤
Related: proposal-XX, proposal-YY
Read when:
- Mesh 編集を Phase 化するとき
- Bone 自由変形を再検討するとき
```

別例:

```md
### AI 動画ガイド

Status: IDEA
Area: AI, Animation
Implementation: NOT_STARTED
Read when:
- AI Engine を実装するとき
- CAF / ClipAsset 周辺の構造を変更するとき
```

---

## メタデータ項目

すべて必須にはしない。

### `Status`

候補:

- `IDEA` — 初期アイデア
- `PROPOSED` — ある程度整理された提案
- `ACCEPTED` — 将来実装する方針として採用
- `PARTIAL` — 一部のみ実装済み
- `IMPLEMENTED` — 実装済み
- `SUPERSEDED` — 別案に置き換え済み
- `REJECTED` — 現時点で不採用

既存のステータス体系がある場合はそれを使用し、新体系を増やさない。

### `Area`

検索・ルーティング用の短い分類。

例:

- Brush
- Canvas
- Renderer
- Timeline
- Animation
- Bone
- Mesh
- Stroke
- AI
- UI
- FileFormat
- Performance

厳密な分類体系を作る必要はない。

### `Implementation`

実装状況を `Status` と分離した方が既存構造に適する場合のみ使用する。

例:

- `NOT_STARTED`
- `IN_PROGRESS`
- `PARTIAL`
- `DONE`

### `Depends`

その案を検討する前提となる機能や設計。

### `Related`

関連 proposal、設計文書、Phase など。

### `Read when`

最重要項目。

内容の要約ではなく、**どの状況なら本文を読む価値があるか** を記述する。

---

# Codex の推奨読書フロー

通常タスクでは、以下を基本とする。

```text
1. 現在タスク / Phase を読む
2. 現在状態・進捗を確認する
3. 必要なら Architecture / 現行仕様を読む
4. proposal index / 計画索引で関連候補を検索する
5. 関連性がある proposal 本文だけ読む
6. 現行コードを確認する
7. proposal を現在の実装へそのまま適用せず、現状に合わせて再評価する
```

重要なのは、proposal index を読んだからといって proposal 本文を全件読む必要はないという点である。

---

# Proposal の扱い

## Proposal は命令ではない

proposal に書かれた内容は、原則として以下のいずれかである。

- 将来候補
- 当時の設計案
- 問題提起
- 未検証のアイデア
- 現在も有効か再確認が必要な設計知識

したがって、関連 proposal を発見した場合でも直接実装へ移らない。

必ず以下を確認する。

1. 現在のコード
2. 現在の Architecture / 正本
3. その後に追加された proposal
4. 既に別方式で解決済みでないか
5. 現在の Phase の目的と一致するか

---

# Single Source of Truth

同じ事実を複数文書で恒久的に管理しない。

例:

- 現在の依存バージョン → package manifest / lockfile を正本とする
- 現在のアーキテクチャ → Architecture 文書を正本とする
- 現在の作業状態 → Progress / Current 文書を正本とする
- 今回の実装範囲 → Phase を正本とする
- 未採用案 → Proposal を正本とする

Phase や proposal 内で他文書の内容を必要以上に複製せず、可能なら参照先を示す。

ただし、Codex が今回の Phase を実行するために不可欠な制約は Phase 内にも明記してよい。

「重複ゼロ」を目標にしない。

---

# 変更しない方がよいもの

以下は、明確な問題が確認できない限り変更しない。

- proposal 本文の大量統合
- 過去 proposal の削除
- Archive の再編成
- 全文書のタグ付け
- 大規模なファイル名変更
- 階層の全面変更
- 既存文書の一括要約
- 新しい管理ツールの導入
- 文書フォーマットの強制統一

これらはトークン削減以上の維持コストや情報損失を生む可能性がある。

---

# 実装方針

Codex はこの提案を受けた場合、直ちに大規模変更を行わない。

まず現状を調査する。

## Step 1: 現在の文書構造を確認

以下に相当する既存要素を探す。

- Codex 向け恒久指示
- 現行 Architecture
- 現在進捗
- Phase
- Proposal
- Proposal / 計画索引
- Archive
- 実装予定一覧

## Step 2: 既にルーティング機能が存在するか評価

次の問いに答える。

- Codex は現在のタスクから関連 proposal を低コストで発見できるか
- proposal 全文を毎回読む必要があるか
- 未実装案と現行仕様を区別できるか
- superseded / implemented な proposal を判別できるか
- 古い提案を後から再発見できるか

既に十分なら変更しない。

## Step 3: 最小改善だけ提案

不足がある場合のみ、既存の索引または最も自然な入口へ以下を追加する。

- Status
- Area
- Read when
- 必要なら Related / Depends

新規ファイルを作るより、既存索引の拡張を優先する。

## Step 4: サンプル適用

全 proposal を一括更新しない。

まず 3〜5 件程度の proposal に適用し、実際に Codex の探索が改善するか確認する。

## Step 5: 効果がある場合だけ拡張

効果が確認できた場合のみ、将来 proposal を触るタイミングで徐々にメタデータを追加する。

既存 proposal の一括移行は必須としない。

---

# 成功条件

この改善は、以下を満たせば成功とみなす。

1. Codex が毎回すべての proposal を読む必要がない
2. 関連する古い proposal を必要時に再発見できる
3. proposal が現行仕様として誤認されない
4. 新しい提案を後から追加しても構造が破綻しない
5. 未実装案へ追記しても検索可能性が維持される
6. 人間側の文書管理負荷がほとんど増えない
7. 既存の TEGAKI ドキュメント構造を大きく壊さない
8. トークン削減のために設計知識を失わない

---

# 非目標

本提案の目的ではないもの:

- TEGAKI の全ドキュメントを完全整理すること
- proposal 数を減らすこと
- 全情報を一つの正規化されたデータベースへ移すこと
- Codex 用の特殊な短縮言語を導入すること
- 人間向け可読性を犠牲にしてトークン数だけを減らすこと
- 過去の設計判断を消すこと

---

# 判断原則

迷った場合は、以下の優先順位を使う。

```text
情報を失わない
    >
再発見できる
    >
現在仕様と将来案を区別できる
    >
Codex が必要情報だけ読める
    >
文書トークンを少し削る
```

TEGAKI では、単純なコンテキスト最小化よりも **探索可能性を維持した疎結合な知識構造** を優先する。

---

# Codex への依頼

この文書は「この方式へ必ず変更せよ」という実装指示ではない。

まず現在の TEGAKI リポジトリのドキュメント構造と Codex 向け指示を調査し、以下を報告すること。

1. 現在すでに実現できている点
2. proposal / 未実装案の探索で無駄が生じている点
3. 情報損失や目詰まりを起こしそうな箇所
4. 変更不要と判断できる部分
5. 実施価値がある場合のみ、最小限の改善案
6. 改善する場合の変更対象ファイルと理由

**大規模整理・大量リネーム・proposal の統合や削除は、調査結果から必要性が確認されない限り行わないこと。**

最適な結論が「現状のままで十分」である場合、それを正式な結論としてよい。
