# UI/UX・アニメーション基盤 再設計提案書
## ―「思考の水位」を揃え、直接操作を中心に据えた描画・アニメーション環境へ―

## 1. 目的

現在のWEBお絵かきツールは、描画、アニメーション、独自ショートカット、Q/V、QTP、マウスホイール操作など、独自の操作体系をすでに持っている。

一方で、特にアニメーションテーブルや変形系GUIについては、機能実装を優先してきたため、視覚構造・配置・導線について再設計できる余地が大きい。

今回の再設計では、Callipeg Studio、Adobe Fresco、CLIP STUDIO PAINT Simple Modeなどに見られるモダンな描画UIを参考にしながら、既存ツールの独自性を失わず、

- 見た瞬間に意味を推測できる
- アプリを跨いでも基本操作で迷いにくい
- キャンバス上の直接操作を優先する
- 高度な数値編集は必要なときだけ呼び出す
- アニメーション・変形・物理演算を共通基盤の上に載せる

ことを目標とする。

---

# 2. 中核思想：「思考の水位」

UI設計上もっとも重視する概念を「思考の水位」とする。

ユーザーが制作中に本来考えたいのは、

- 何を描くか
- どう動かすか
- タイミングはどうするか
- ポーズをどう変えるか
- どの程度揺らすか

といった制作そのものについてである。

一方、

- 再生ボタンはどこか
- 変形モードはどこか
- パネルをどこから開くか
- 数値欄をどこで変更するか

といったUI探索は、制作より一段低い思考を要求する。

この低い水位へ頻繁に降ろさないことを設計目標とする。

したがって、

> 一般的な操作は既知の視覚文法へ寄せ、独自化するのは制作速度や表現力に実際の利益がある部分だけとする。

---

# 3. Callipeg/Fresco/CLIP STUDIO Simple系へ寄せる範囲

完全なUI互換を目指すものではない。

参考にするのは主に、

- 単純な色面
- 装飾的グラデーションを使わない
- 過剰な縁取りを行わない
- 大きめの角丸
- 単色SVG
- 選択状態のみアクセント色を強くする
- Canvas First
- 直接操作中心
- コンテキスト依存UI
- 再生など重要操作の視認性
- ツール種別による操作領域の切り替え

といった視覚・操作文法である。

SVGそのものや細かな配置を複製するのではなく、同程度の情報密度・コントラスト・余白・視線誘導を持つ独自デザインへ換骨奪胎する。

---

# 4. 独自性として維持する要素

以下は他アプリへ合わせるために削除・変更しない。

- Q/V
- QTP
- 半透明パネル
- マウスホイール操作
- 独自ショートカット
- 二段構成を許容するアニメーション操作列
- WEBツールとしての軽快さ
- 将来の物理演算
- 将来のAI補助
- 独自投稿フロー
- 独自の描画補助

つまり、

> 視覚文法は共有するが、操作能力は共有しすぎない。

---

# 5. 半透明Panelをデザイン上の特徴として維持する

Callipeg等のフラットデザインを参考にする一方、本ツールでは半透明Panelを維持する。

目的は、

- CanvasをPanel裏まで連続して感じさせる
- 画面を広く感じさせる
- QTP等のフローティングUIによる圧迫感を軽減する

ことである。

構成としては、

```text
Canvas
↓
Translucent Panel Surface
↓
高コントラストのSVG / Text
↓
Accent ColorによるActive表示
```

とする。

Panel自体を透明にしても、アイコンや文字まで薄くしない。

また、

- gradient
- bevel
- 強いdrop shadow
- 装飾的border

には頼らない。

「透明感」は残すが「装飾感」は抑える。

---

# 6. Design Token化

色や角丸を個別CSSへ直接書かず、共通トークンへ集約する。

例：

```text
surface.canvas
surface.panel
surface.panelFloating
surface.popup

border.subtle

text.primary
text.secondary
text.disabled

icon.normal
icon.active
icon.disabled

control.hover
control.pressed
control.active

accent.primary

timeline.default
timeline.selected

onion.previous
onion.next
```

角丸：

```text
radius.small
radius.control
radius.panel
radius.capsule
```

透明度：

```text
opacity.panel
opacity.panelFloating
opacity.disabled
opacity.onionNear
opacity.onionFar
```

今後UIを追加した際、自動的に同じデザイン言語へ乗る状態を作る。

---

# 7. 左サイドバー

左サイドバーは現在の機能配置思想を維持する。

外観のみ、

- 縦長
- 上下端を丸くする
- 単色SVG
- 通常時は低主張
- Active時のみアクセント色
- ボタン間の余白を統一

する。

CallipegやSimple Modeのような「ツールの存在は見えるがCanvasより主張しない」状態を目標とする。

---

# 8. Q/Vを身体側へ移動できるUIとする

Q/Vは独自機能として強化する。

ドラッグによって、

```text
左上
左中央
左下

右上
右中央
右下
```

などへ移動可能とする。

必要なら自由ドラッグ＋アンカースナップ方式とする。

これは単なるカスタマイズではなく、

> 利き手・ペン・Panel配置に応じて、高頻度操作を身体の近くへ移す

ための仕組みとする。

全UIを自由配置可能にするのではなく、重要な装置だけを移動できる「制約された自由」とする。

---

# 9. QTPは維持する

QTP等の自由移動・開閉可能なTool Panelは本ツール独自の強みとして維持する。

ただし、

- Panel surface
- Slider
- Toggle
- SVG
- Active state
- Radius
- Spacing

については固定UIと同じDesign Systemを使用する。

---

# 10. 右上Quick Control Table

現在ショートカット中心となっている表示系操作は、UI安定後に右上へ小型テーブルとして追加することを検討する。

候補：

- Undo
- Redo
- 左右反転
- 上下反転
- Canvas回転
- 回転リセット
- 表示位置リセット
- 100%表示

ただし機能をすべて常駐させない。

使用頻度と視認価値を評価して削減する。

---

# 11. アニメーションテーブルを再設計する

アニメーションテーブル周辺は今回の主要再設計対象とする。

既存機能は極力維持し、配置と視覚構造を刷新する。

特に再生操作は中央付近に配置する。

```text
        Animation Controls

     [Prev] [ PLAY ] [Next]

[Onion][Loop][Cycle][その他]
```

必要であれば二段構成を正式採用する。

Callipegと同じ一段構成へ無理に合わせない。

重要なのは、

- 再生
- 時間移動
- セル操作
- Onion
- Cycle
- 表示補助

の意味的まとまりが視覚上も成立すること。

---

# 12. Animation TableはDock型へ

完全フローティングではなく、

- Bottom Dock
- Right Dock
- Left Dock
- Hidden

を基本とする。

幅または高さをSplitterで変更可能とする。

```text
┌───────────────────────┐
│        Canvas         │
├───────────────────────┤
│      Animation        │
└───────────────────────┘
```

または、

```text
┌────────────────┬──────┐
│                │      │
│     Canvas     │ Anim │
│                │      │
└────────────────┴──────┘
```

左右配置があることで、将来Graph Editorを縦長に使用する場合にも対応できる。

---

# 13. 既存Wheel / Shortcutを不変条件とする

リデザインによって、

- Canvas zoom
- Frame送り
- Timeline navigation
- Wheel
- Keyboard shortcut
- Q/V
- Pointer gesture

を変更しない。

Codex実装時の明示的な不変条件：

> Visual redesign must not alter existing wheel, keyboard, pointer, gesture, Q/V or timeline behavior unless explicitly requested.

---

# 14. 変形システムの基本思想

変形系UIでは、

> Direct Manipulation First

を基本とする。

つまり、

```text
Canvas上で直接操作
        ↓
必要なら簡易GUI
        ↓
さらに必要なら数値Inspector
```

という三段構造にする。

数値入力を最初から表示しない。

多くの制作場面では、

- 数px正確に動かす
- 37.5度に回転する
- 103.2%へScaleする

ことより、

「見た目としてこの位置」

へ置くことの方が多いと想定する。

そのため数値入力は重要だが、副次的な精密操作と位置付ける。

---

# 15. Layer Transform GUI

Layer Transformについては、Callipeg / Fresco / CLIP STUDIO Simple系の思想へ比較的強く寄せる。

基本画面ではキャンバス上に、

- Bounding Box
- Corner Handle
- Edge Handle
- Rotation Handle
- Pivot

など必要最小限の直接操作UIだけを表示する。

詳細な数値Panelは常時表示しない。

通常：

```text
┌─────────────┐
│             │
│    Layer    │
│             │
└─────────────┘
       ○
```

ユーザーは直接ドラッグする。

必要な場合のみ、

```text
Transform ▼
```

などからInspectorを展開する。

---

# 16. Transform Inspectorは折りたたみ式

数値操作を必要とするユーザー向けに、

```text
Position
X
Y

Scale
W
H

Rotation

Opacity
```

等を提供する。

ただし初期状態では閉じておく。

展開方式候補：

- 小型Popover
- QTP内
- Side Inspector
- Animation Panel内Inspector

のいずれかとする。

Canvasを数値Panelで常時狭めない。

---

# 17. Transformの二層操作

通常ユーザー：

```text
ドラッグ
↓
目で確認
↓
完了
```

精密操作ユーザー：

```text
直接操作
↓
Inspectorを開く
↓
数値補正
```

とする。

直接操作と数値操作を競合させない。

---

# 18. Modifier Keyによる高度変形

通常Transformを複雑なTool Modeへ分割しすぎない。

例えばCorner Handle操作中に、

```text
Ctrl + Corner Drag
```

で四隅独立変形へ一時切替する。

通常：

```text
Uniform / Affine Transform
```

Ctrl：

```text
Quad / Perspective Transform
```

Shift：

```text
Aspect / Axis Constraint
```

など、既存ショートカット体系との整合を取る。

高度操作を必要としないユーザーには存在を意識させない。

---

# 19. PerspectiveとMesh Warpは別概念として保持する

四隅を独立して動かす変形と、メッシュによる局所変形は内部では区別する。

```text
Transform
├ Affine
├ Quad / Perspective
└ Mesh Warp
```

とする。

ただしUI上は同じTransform Familyとして扱う。

---

# 20. 画像変形とアニメーション内Mesh Transformを同一エンジンへ統合する

画像編集側のMesh Warpと、Animation Table側で使用するMesh Transformは、別実装にしない。

共通のDeformation Engineを使用する。

概念としては、

```text
Deform Engine

Static Image Edit
        │
        ├── Mesh Warp
        ├── Perspective
        └── Transform

Animation
        │
        ├── Mesh Keyframe
        ├── Transform Keyframe
        └── Physics
```

とする。

違いは「変形機能」そのものではなく、

> その状態を画像へ確定するのか、時間軸上のパラメータとして保持するのか

である。

---

# 21. Transform / Deform Stateを共通データとして扱う

内部的には、

```text
TransformState
DeformState
MeshState
```

などとして変形状態を表現し、

Static編集では、

```text
State → Apply / Bake
```

Animationでは、

```text
State → Keyframe
```

とする構造が望ましい。

こうすることで、

画像編集で作った変形をそのままAnimationへ利用したり、

Animation上のあるPoseを静止画像として確定する、

といった相互利用もしやすくなる。

---

# 22. Meshそのものを第一級オブジェクトへ

将来的にはMeshを、

「変形ツール使用中だけ存在する一時UI」

ではなく、

```text
Mesh
 ├ Vertices
 ├ Edges
 ├ Faces
 ├ Control Points
 └ Deformation Parameters
```

を持つ再利用可能なオブジェクトとして設計することを検討する。

これにより同一Meshを、

- 静止画Warp
- Animation
- Physics
- Bone / IK
- AI補助

へ発展させられる。

---

# 23. Animation Transform GUIもCanvas First

Animation中にLayer Transformを行う場合も、基本操作はCanvas上とする。

ユーザーがオブジェクトを直接、

- 移動
- 回転
- Scale
- Perspective
- Mesh Warp

し、その結果が必要に応じてKeyframeへ反映される。

Animation Panel側に大量の数値Sliderを並べることを基本設計にはしない。

---

# 24. 数値・Sliderは「選択時に必要なら出る」

Animation Transformでは、対象を選択しただけで巨大な設定Panelを開かない。

例えば、

```text
Layer selected

[Transform]
[Mesh]
[Physics]
```

程度の小さな入口を表示する。

Transformを開いた場合のみ、

```text
Position
Rotation
Scale
Opacity
```

を表示。

Meshを開いた場合のみ、

```text
Mesh density
Influence
その他
```

を表示する。

Progressive Disclosureを徹底する。

---

# 25. Sliderの役割

Sliderは、

「数値を正確に入力するため」

ではなく、

「画面を見ながら値を素早く探索するため」

に使う。

したがって、

```text
Slider + optional numeric field
```

とする。

Slider操作中：

```text
視覚変化をリアルタイム確認
```

必要な場合だけ数値入力。

つまり優先順位は、

```text
Direct Drag
>
Slider
>
Numeric Input
```

とする。

---

# 26. Cycle / Linked Instance

蜂の羽ばたき等の反復については、単純なCopy & PasteではなくCycleを第一級概念として扱うことを検討する。

```text
A B C
↓
Cycle
↓
A B C A B C A B C
```

元データを参照するLinked Instance方式を基本とする。

修正：

```text
Bを修正
↓
すべてのB Instanceへ反映
```

将来的に、

- Loop
- Ping-Pong
- Random
- Count
- Speed

などを扱える構造を目指す。

---

# 27. Onion Skin

過去と未来を瞬間的に区別できる色設計へ変更する。

```text
Previous
Current
Next
```

だけでなく、距離によってOpacityを変える。

```text
Previous 3
Previous 2
Previous 1

Current

Next 1
Next 2
Next 3
```

色・枚数・透明度は設定可能にする。

Callipeg等を参考にするがRGB値そのものは複製しない。

---

# 28. Generic Graph Editor

Graph EditorはPhysics専用にしない。

共通Parameter Editorとして設計する。

対象：

```text
Position X
Position Y
Rotation
Scale
Opacity

Mesh Parameter
Physics Weight
Spring
Damping
その他
```

横軸：

```text
Time
```

縦軸：

```text
Value
```

とする。

---

# 29. Direct ManipulationとGraph Editorの関係

Canvas上で操作：

```text
Layerを移動
```

↓

```text
Keyframe生成
```

↓

```text
GraphへCurve表示
```

↓

必要なら、

```text
Ease / Tangent / Physicsを編集
```

という流れを目標とする。

通常ユーザーはGraph Editorを開かなくてもAnimation可能。

高度な調整時だけGraphへ降りる。

ここでもProgressive Disclosureを維持する。

---

# 30. GuidePathを共通基盤へ

移動軌道、描画ガイド、中割り補助等を別々に実装せず、共通Path構造を検討する。

```text
GuidePath / BezierPath
```

を、

- Drawing Guide
- Motion Path
- Inbetween Guide
- Physics reference
- IK guide

などから利用する。

---

# 31. Motion Path

Canvas上で、

```text
● Start
 ╲
  ╲
   ╰────● End
```

のような曲線を直接編集する。

オブジェクトをPathへ拘束し、

```text
position = path(t)
```

としてAnimation可能にする。

Graph Editorでは、

```text
Path Progress
0 → 1
```

を編集可能とする。

これによりMotion PathとEasingを自然に統合できる。

---

# 32. 将来のPhysicsとの接続

共通Transform / Mesh / Graph基盤ができれば、Physicsはその上に載せる。

例えば、

```text
Base Transform
↓
Animation Curve
↓
Physics Modifier
↓
Final Transform
```

とする。

Meshについても、

```text
Base Mesh
↓
Manual Keyframe
↓
Physics Deformation
↓
Final Mesh
```

という構造を検討できる。

---

# 33. AIも同じ基盤を利用する

AI機能のために別のAnimation Systemを作らない。

AIは、

- Motion Path候補
- Mesh Control Point候補
- Inbetween対応点
- Curve候補
- Physics Parameter候補

などを提示する補助レイヤーとして使う。

人間が最終操作できる既存パラメータへAI結果を流し込む。

---

# 34. UI階層

今回のGUI設計を一言で整理すると、

```text
Level 1
Canvas上の直接操作

Level 2
簡易Button / Slider / Modifier Key

Level 3
Inspector / Numeric Input

Level 4
Graph Editor / Advanced Parameters
```

とする。

ユーザーを最初からLevel 3、Level 4へ連れていかない。

必要になったときだけ深いUIへ降りる。

---

# 35. 「思考の水位」とTransform UI

Transform UIでは特にこの原則を重要視する。

ユーザーが、

「右へ少し動かしたい」

と思った場合、

```text
X = 143 → 151
```

と考えさせない。

そのまま右へドラッグさせる。

「正確に8px動かしたい」

場合だけ数値を使用する。

UI側がユーザーの思考を不必要に数値へ翻訳させない。

# 37. Codex実装時の禁止事項

UI改善を理由として、明示的な指示なしに以下を変更しない。

- Wheel behavior
- Keyboard shortcuts
- Q/V behavior
- QTP behavior
- Pointer gestures
- Drawing Engine
- Animation data
- Save format
- Timeline semantics
- Existing tool meaning

また、静止画MeshとAnimation Meshを別々の変形エンジンとして実装しない。

共通化可能性を最初に検討する。

# 38. 成功条件

今回の再設計は「Callipegに似たか」だけで評価しない。

以下を満たすことを成功条件とする。

- 主要操作が視覚的に推測できる
- Canvasが広く感じられる
- 半透明Panelの独自性が維持される
- 再生操作が即座に見つかる
- Animation UIが整理される
- TransformがCanvas上だけで基本操作できる
- 数値Panelが作業を邪魔しない
- 必要なユーザーには精密入力も提供される
- PerspectiveとMesh Warpを将来的に統合可能
- StaticとAnimationが同一変形基盤を使う
- Graph Editorを後付けできる
- Physicsを同じParameter体系へ載せられる
- Q/V、QTP、Wheel等の独自高速操作を失わない
- Callipeg等との二刀流時に認知切替が小さい

# 39. 最終方針

本ツールは、

「CallipegのWEB版」

を目標としない。

Callipeg、Fresco、CLIP STUDIO Simple系で成熟している、

- 視覚的な単純さ
- Canvas中心設計
- 直接操作
- コンテキストUI
- 必要なときだけ詳細を出す設計

を参考にする。

その上で、

- 半透明Panel
- Q/V
- QTP
- Wheel
- 独自Animation UI
- Shared Mesh Engine
- Physics
- AI

を本ツール独自の方向として発展させる。

共通部分ではユーザーの思考を節約し、独自部分では制作能力を拡張する。

目標とする使用感は、

> 見た瞬間には馴染みがある。  
> 基本操作では迷わない。  
> しかし使い込むほど、このツール独自の高速な操作と高度な表現能力が現れる。

ことである。

特にTransformについては、

> 「数値を操作する」のではなく「絵を操作する」。

Animationについては、

> 「パラメータを編集する」のではなく「動きを編集する」。

という感覚を第一にする。

数値、Slider、Graph、Mesh Parameterは、それを必要とする場面でのみ水面下から取り出せる専門工具として配置する。
