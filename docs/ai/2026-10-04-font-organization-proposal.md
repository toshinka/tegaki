# フォントのジョグ選択・外部保管・一軸整理案

状態: REFERENCE / 検討案。2026-10-04。製品実装・27書体の移設は未実施、追加DLは保留。
基準: 現行WP-021、STATUS/TECHNICAL、font-library.js、balloon-popup.js。既存差分を保持。

## 推奨

Eドライブに元フォントと作者資料を保管し、アプリの一軸ツリーで表示順・収納先を管理する方式。主役はツリー直下、その他は折りたためるジャンルへ置く。物理ファイルを動かさずに表示分類を変更できる。Windowsで作ったフォルダは初回読み込み時の分類の種として利用できるが、以後のアプリ内分類とは同一ではない。この区別をUIで明示する。

Windowsのフォルダ配置を常にそのままツリーへ反映したい場合は、下表Bの方が合う。A/Bを混ぜて双方を自動的に正本とする方式は採らない。

## ジョグ選択

- フォント欄にポインターがある時のホイールで前後の書体へ移動。既存選択と同じ適用経路を使い、書体名と選択中の見本を更新する。
- 上向きで前、下向きで次。端では停止し、勝手に先頭へ循環しない。フォルダ見出し・無効行は飛ばす。
- 細かなタッチパッド入力は蓄積し、通常ホイールは一段階ずつ。Ctrl+wheelのブラウザ拡大は横取りしない。
- ポップアップ本体の通常スクロールは保持。開いたツリー上はリストのスクロール、閉じた選択欄上は書体切替とする。
- 名前は即時更新。高速連続入力中は100〜150ms程度の落ち着きを待って最後の対象の実体を読み、古い非同期結果は見本へ反映しない。全候補の一括先読みはしない。感触はBrowser/Owner操作で調整する。
- 作品確定前の選択はUI設定のみ。文字LayerのHistoryをホイール一刻みで増やさない。

## 一軸ツリー

現状はnative select/optgroup。nativeメニューに折り畳み・入れ子・独自D&Dを加えることはできないので、現在の小さな選択欄から開く部分を独自の一軸ツリーへ置き換える。独立した大型管理画面は作らない。キーボード上下・左右開閉・Enter選択・Escape閉じも用意する。

主役は直下、下に「手書き」「丸文字・かわいい」「太字・ポップ」「鋭角・クール」「筆」「ドット・電子」「装飾・MV」等を置く。これは初期配置案で、手動順序と名前を優先できる。形が主分類、感情/MV/用途は複数タグにして、ひとつの書体を各所へ複製しない。

D&Dで同階層の上下入れ替え、フォルダ内への収納、直下へ戻す操作。説明欄のお気に入り近くに「収納先: 直下 / …」を追加し、ドラッグなしでも同じ分類操作を行える。上下移動ボタンも代替として用意する。自分を子にする/子孫へ移す循環は禁止。

手動順序が基本。favoriteチェックで編集途中に行が跳ぶと整理しにくいため、通常の並びは保持し、「お気に入りを上へ」は表示切替にする案を推奨。Primaryは書体の既定選択、favoriteは好み、直下配置は普段の露出度として別に扱う。

## Eドライブの保管

Owner依頼により、空の置き場だけ作成済み。

```text
E:\Data\TegakiFonts\
  Library\           元フォント・LICENSE・readme・sourceを一書体単位で保管
  Inbox\             Ownerが追加した未監査のfont/zip/作者資料
    URLメモ\         雑なURL、.urlショートカット、テキストだけでも投入可能
```

URLは**残す方を推奨**。検索し直すより、作者・取得版・無料/有料の違い・当時の条件をたどりやすい。必須入力にはしない。「書体名またはzip名＋URL」だけで十分。fontと同じ名前のテキストや同じ小フォルダに置くと対応が明確。URLだけの候補はURLメモへ入れ、後でAIが紐づける。AI整理後も元メモを保持し、作者資料を置換しない。

未監査Inboxは導入済みリストへ自動登録しない。許諾・配布元・実体・分類を確認してから登録。既存27書体のIDを維持し、ファイル名やフォルダが変わっても作品の再編集参照を壊さない。hashで内容同一性を検査する。UI設定を移す場合もProject保存schemaは変えない。

表示フォルダ・手動順序はブラウザUI設定として持ち、必要ならフォント一覧の整理設定をEへエクスポートできるようにする。Eの元実体と作者資料をAIが後で調査可能にしておく。ローカルAIは許可されたEの資料を読めるが、GitHubしか見ない外部AIには実体を渡さない運用となる。

## ブラウザとの接続・再配布

ブラウザは `E:\Data` という文字列だけで任意ファイルを読めない。初回にOwnerがフォント用rootを選ぶ。Chrome/Edge系でFile System Access APIを使い、選んだrootのhandleを保存、利用時に権限を確認する。ブラウザ/設定によって再許可が必要。非対応環境では本人ファイル取り込みを代替とする。[Chrome公式](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)、[MDN directory picker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker)。

フォント選択時に元ファイルを読む設計なら、Viteの公開ディレクトリやHTTP配信対象へEを公開する必要がない。フォント実体をGitの管理外へ出すだけでなく、build成果物に入れず、取得cache/公開ディレクトリ/配布zipに元データを残さないことも確認する。許諾禁止のある書体をプライベートな場所へ置くこと自体が、商用/アプリ埋込み等の条件を変えるわけではない。

現checkoutの `public/fonts` は未追跡だが製品buildへコピーされる。移設は、Eへの複製→hash確認→外部実体参照で既存IDを解決→Browser再編集/Project往復→公開側のコピー除去/混入防止、の順に行う。現在は製品参照が公開側を使っているので、コピーだけ先に消さない。

Windows実フォルダをアプリから動かすBの「収納先」は、実ファイル移動である。Chrome公式資料では通常のローカルfile/directoryに対するmoveに制限があり、単純な表示D&Dと同じ工数ではない。まずWindowsで物理移動＋再走査に限定する案が堅実。[移動APIの制限](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access#renaming-and-moving-files-and-folders)。

## 後続の順序

1. ホイールによる選択・見本更新を限定実装。
2. A/Bの分類正本を決め、一軸ツリー・手動順序・収納先を実装。
3. 外部root接続と27実体移設。既存IDの維持・権限切れ・ファイル欠落を検証し、Git/build配布対象から実体を外す。
4. その状態を確認してから追加監査・DLを再開。感情/MV/手書きの幅を優先し、かな専用を減点しない。Owner追加はInbox経由で同じ監査へ乗せる。
