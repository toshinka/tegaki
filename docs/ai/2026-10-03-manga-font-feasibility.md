## 分類・チェック項目

主分類は字形: アンチゴチ / 角ゴシック / 丸ゴシック / 明朝 / 手書き・筆 / 装飾。装飾は角張り・長体・レトロ・ドット・崩れ等の副タグで整理する。「カワイイ」だけを形の分類にしない。

用途タグは複数: 標準セリフ / 強調 / 心の声 / ナレーション / 放送・機械 / 擬音 / 見出し / MVテロップ。感情タグも複数: 怒り / 恐怖 / 震え / 弱さ / 喜び / 柔らかさ / 不穏。手書きは字形分類としてまとめ、用途・感情を併記する。

調査台帳に残す項目:

- 正式名・作者・version・配布元・ライセンスURL・確認日・取得物hash・元画像。
- 商用の印刷/電子作品/動画、同人誌、Webfont、アプリ同梱/再配布、SVGへの埋め込み、改変/形式変換。用途別に可/不可/未確認と条件を記録。
- 必須登録・SNSいいね/フォロー/投稿・連絡・表示義務。任意の応援依頼と必須条件を区別する。
- かな・漢字収録範囲・英数字・約物・ウェイト・縦書き・縦中横。漢字ありだけで十分な収録とは判断しない。
- 特殊濁点: 結合濁点対応 / 私用領域のみ / 未対応 / 未確認。特定書体の外字入力と通常文字を区別。
- 作者説明による確認、fontのcmap/GSUB確認、Tegaki実描画確認を別欄にする。代替フォントで見えている文字を対応済みと扱わない。

商用不可は基本除外。ただし明示的に同人誌の頒布を許可するものは「同人誌限定」の候補枠へ残し、商用/MV候補とは区別する。SNS必須・煩雑な申請条件は除外。条件不明は保留として自動採用しない。

制作物への利用許可とフォント実体の配布は別。[OFL公式FAQ](https://openfontlicense.org/ofl-faq/)もこの違いを説明している。既存組版は取り込みフォントをSVGへ埋め込むため、商用画像可だけで採用しない。

## 選択UIの候補

一覧の一行: `☆  書体名  お手本文字  極短評  用途/対応バッジ`。お気に入りチェックを付け、ONの項目を安定した順で上へ集める。ユーザー短評と調査側の説明は別に保存する。標準のお手本はかな・漢字を混ぜ、入力中のセリフにも切替可能にする。

縦書き見本と「あ゙・ん゙・!?・…・ー」等の確認用見本を用意。未対応文字は欠落を示し、fallbackで通ったように見せない。

Primaryは通常セリフの既定選択。お気に入りは一覧でよく使う集合。スロットは手動登録した即選択枠（例: 標準/強調/心の声/恐怖/ポップ/自由）。お気に入りのソートが変わってもスロット割当は動かさない。最初はPrimary＋お気に入りで使い勝手を確認し、スロットは必要なら追加する。

表示用分類・短評・許諾台帳と、ユーザーのお気に入り/Primary/スロットはフォント管理側の情報。Projectへフォント実体を混入しない。未取得のフォントをPrimary指定した時の導線、フォント欠落時の再編集通知、環境スナップショットとの関係は実装Cardで定義する。

大量搭載時は一覧表示のために全フォントを毎回読み込まず、表示中の見本・選択中の書体だけロードする。現行listFontsはIndexedDB getAll後にdataを取り除く実装なので、大量導入前にメタデータ読取りの費用を測る。

1. 推薦11枚とスクショの漫画候補を抽出・重複統合。まず8〜12書体を対象に公式条件と分類台帳を作る。ここで一次候補をOwnerへ提示する。
2. 採用候補だけ作者の配布導線から取得し、ライセンス/readme・hash・versionを保存。OSへの一括インストールは不要。商用/同人誌枠を分けてブラウザの既存取り込み経路で試す。
3. 同じ見本の縦横組版、特殊濁点、漢字欠落、プレビュー/確定画素を確認してPrimaryを選ぶ。
4. 文字タブ移設とフォント選択UIを別の限定Cardで実装。関連verifier・buildに加え、実Browserで確定/再編集/Undo/Redo/Project往復を確認する。Owner受入は別。
5. 感情系を補充し、その後にMV/ポップ・手書きへ広げる。全851種の取得は行わない。

LUNA MAX（このrepoの定義に合わせgpt-5.6-luna / max）は、独立した画像バッチと決まった表形式の抽出を担当。今回の試行は残りの推薦6画像だけに限定し、閲覧/抽出のみ、追加探索・ライセンス断定・writeなしとした。

本調査は1バッチ15〜25候補を目安に同じ担当を再利用。確定名・用途・元画像・不明点だけ返し、全文ログや全会話を毎回渡さない。公式許諾の確認と最終採用は親が担当し、重複調査を避ける。画像から名前を読めないものだけ原寸へ戻る。

完了通知を優先し、長時間作業の巡回はrepoのDEVELOPMENTに従い10〜15分程度。親は別の独立作業を進め、完了・失敗・入力要求だけ対応する。モデルのmax指定はトークン節約を保証しない。バッチの結果数・未確定数・利用量が取れる場合は記録して大きさを調整する。

[OpenAI公式のmulti-agent案内](https://developers.openai.com/api/docs/guides/responses-multi-agent)は独立した限定作業への委任を推奨し、子agentの追加でトークンが増える場合もあると説明する。本件では並列数を増やすより、画像の重複排除・限定バッチ・同じ結果の再読回避を優先する。
