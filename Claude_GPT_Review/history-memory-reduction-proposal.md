# Tegaki History省メモリ化 改修提案書

更新日: 2026-09-01
作成: 外部AI（Web版Claude）
前提: SSD/ディスクへの退避を主軸にせず、メインメモリ上での確保を優先する。ディスク退避は「サブな逃げ道」程度の位置づけに留める。件数（現行500）が結果的に減ることは許容範囲とする、というOwnerの方針を前提とする。
位置づけ: 実装契約ではなく、CODEXへの検討材料として提出する提案書。

---

## 1. 結論（先に）

ご提示の方針（RAM優先、disk swapは補助止まり、件数減少は許容）は**技術的に実現可能**であり、しかも**現状の実装を素直に直すだけで、件数を意図的に減らさなくても実質的な改善が見込める**可能性が高いことが分かりました。理由は、前回お伝えした通り、現状の重さの原因が「差分ではなく毎回レイヤー全体を無圧縮で複製している」という一点に集約されるためです。ここを直せば、通常のペン入力は大幅に軽くなり、逆に塗りつぶしや変形のような「本来重い操作」だけが今まで通り重いまま残る、という**操作の実態に応じた自然な差**になります。「500件を一律300件にする」よりも、この方が筋の良い着地点だと考えます。

---

## 2. 現状の原因（前回の要約）

`system/drawing/brush-core.js`の`_recordStrokeHistory()`は、1ストロークごとに`createLayerRasterSnapshot()`（`system/layer-system.js`）を呼び、**レイヤー全体のピクセルをGPUから無圧縮で読み出し**、変更前後の2枚を丸ごと保持しています。さらに`system/raster-snapshot-memory.js`側で、そのレイヤーに描かれた**全ストローク分の点列データ（pathsData）も毎回まるごと複製**しています。1200×1200キャンバスで13エントリ・463MBという数字は、この2つの積み重ねの結果でした。

---

## 3. 技術的実現性の確認

### 3.1 差分（変更範囲だけ）の保存はPixiJSの機能で実現できる

現在使用しているPixiJS v8系の`renderer.extract.pixels()`は、`frame`オプションで**矩形範囲を指定した部分抽出**に対応しています。

```js
// 現状: レイヤー全体を抽出
renderer.extract.pixels({ target: sprite, clearColor: '#00000000' });

// 変更範囲だけを抽出する場合
renderer.extract.pixels({
    target: sprite,
    frame: new Rectangle(dirtyX, dirtyY, dirtyWidth, dirtyHeight),
    clearColor: '#00000000'
});
```

出典: https://pixijs.download/release/docs/rendering.BaseExtractOptions.html

一点だけ留意点があります。過去のPixiJSバージョン（6.4.2前後）で、`frame`に特定のサイズを渡すとWebGLエラーになる不具合が報告されていました（出典: https://github.com/pixijs/pixijs/issues/8426）。Tegakiは既にv8.19.0まで更新済みなので、この不具合自体は解消されている可能性が高いですが、**実装前に小さなプロトタイプで実機確認しておく**ことを推奨します。

### 3.2 「変更範囲」を求めるための土台は既にコード内にある

`system/raster-bounds.js`には、`calculateOpaqueRasterBounds()`（不透明ピクセルの範囲を求める）、`unionRasterBounds()`（複数の範囲を1つに結合する）、`normalizeRasterBounds()`など、範囲（bounds）を扱う一連のユーティリティが既に存在します。ストローク中に触れた座標の最小/最大を追跡する処理を`brush-core.js`側に新設し、この既存ユーティリティ群と組み合わせれば、「今回のストロークがどの矩形範囲に影響したか」を求めること自体は、ゼロから設計する必要はなさそうです。

### 3.3 pathsData/pathsの複製方法も見直せる

現状は「レイヤーの全履歴分の点列」を毎回まるごと複製していますが、これは差分保存に切り替えられます。各Historyエントリには**そのストローク自身の点列だけ**を持たせ、レイヤー全体のpathsDataは「基準状態＋それ以降のコマンド列」から必要な時にだけ組み立てる形にすれば、セッションが進むほど複製コストが増えていく現状の問題（400件あたりから重くなる体感の一因）も解消できます。

## 4. 提案する設計

| # | 内容 | 効果 |
|---|---|---|
| A | ペン・消しゴム等、範囲が限定される操作は、影響範囲（dirty rect）だけをbefore/after保存する | 典型的な小〜中サイズのストロークで、保存量を数十〜数百分の1に削減できる可能性が高い |
| B | pathsData/pathsは、そのストローク単体の差分だけを保持する形に変える | セッションが進むほど重くなる現状の複合的な悪化を解消する |
| C | 塗りつぶし・キャンバス全体への変形・レイヤー結合など、本質的に全体へ影響する操作は、引き続きレイヤー全体を保存する | 無理にこれらまで差分化しようとせず、素直に「重い操作は重いまま」とする。既存の`_enforceLimits()`（バイト上限に達したら古い順に削除する仕組み）が、こうした重いエントリが増えた場面で自然に実効件数を絞ってくれる |

C.は重要なポイントです。**現状のバイト上限による自動削除（`HistoryManager._enforceLimits()`）自体は、既に「重いエントリが多い時は実効件数が減る」という設計思想を持っています。** 問題は「軽いはずの操作まで重いデータとして記録している」ことであって、この上限管理の仕組み自体は変える必要がありません。A・Bを直すだけで、この既存の仕組みが正しく機能するようになります。

## 5. 「500件が300件程度に減るのは仕方ない」という前提の再検討

ご提示いただいたこの前提そのものについて、少し違う見方もできると思ったので記載します。

A・Bの改修が実現すると、**典型的なペン入力中心のセッションでは、むしろ500件に近い実効件数を維持できる可能性が高い**です。理由は、通常の1ストロークの影響範囲は、キャンバス全体よりずっと小さいことがほとんどだからです（1200×1200キャンバスに対して、ペン1本のストロークが数十〜数百px四方に収まることは多いはずです）。

一方で、塗りつぶしや全体変形を多用するセッションでは、そうした重い操作の割合に応じて、実効件数が自然に少なくなります。これは**300という固定の数字を目指すのではなく、「軽い操作は軽く、重い操作は重く」という、操作の実態に即した可変の挙動**です。個人的には、この方が「なぜいつも300しか使えないのか」という新たな疑問を生まずに済む、良い着地点だと思います。

ただし、これは差分化の効果がどの程度出るかを実際に測ってみないと確証が持てない部分でもあります。5章の内容は「300への固定的な削減は不要かもしれない」という仮説であり、実測での検証が前提です。

## 6. ディスク退避（サブな逃げ道）について

ご方針の通り、これは初期実装の対象からは外し、優先度を最低に置くのが妥当だと考えます。4章の改修だけで多くの場面は十分に軽くなるはずなので、まずはそちらを先に測定してから、それでもなお足りない極端に長いセッション（例えば1回の作業で1000ストローク以上等）だけを想定した、**最終防衛ラインとしての位置づけ**に留めるのが良いと思います。Kritaも「まずUndo情報から」ディスクへ逃がす設計でしたが、これはメモリが逼迫した時の最後の手段であり、常用を前提とした設計ではありませんでした。同じ考え方で問題ないはずです。

## 7. リスク・検証項目

- PixiJS `frame`付き`extract.pixels()`の実機動作確認（3.1の過去不具合が現行バージョンで再発しないか）。
- 塗りつぶし・変形など「全体保存のままでよい操作」の一覧化。どの操作が差分化対象で、どれが対象外かの線引きを、実装前に明確にしておく必要があります。
- pathsDataの差分化（4章B）は、Undo/Redoの正しさに関わる部分なので、既存の`verify-*.mjs`のようなfixtureベースの検証を新設した方が安全です。
- 実測: 差分化後、典型的なセッションで実際にどの程度のエントリ数・メモリ量になるかを計測し、5章の仮説（300への固定削減は不要かもしれない）を確認する。

---

## 8. 進め方の提案

このプロジェクトの既存のGate文化に沿うなら、次のような段階が考えられます。

1. **計測Gate**: まず現状のまま、典型的な制作セッション（実測でよい）でストロークごとの`byteSize`分布を記録し、「小さいストロークがどれだけ軽くなり得るか」の見込みを数値で確認する。
2. **Aの実装Gate**: dirty rect保存を、まずペンツール1つだけに限定して試験導入し、Undo/Redoの正しさをfixtureで検証する。
3. **Bの実装Gate**: pathsDataの差分化。Aとは独立した変更なので、別Gateに分けた方がリスクを切り分けやすいと思います。
4. **他ツールへの展開**: 消しゴム・塗りつぶし等、他の描画ツールへ順次適用する。
