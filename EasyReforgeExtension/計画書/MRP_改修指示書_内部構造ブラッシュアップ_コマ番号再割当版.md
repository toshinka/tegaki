# Manga Region Prompter 改修指示書
## 内部構造ブラッシュアップ＋コマ番号再割当版

対象は EasyReforge 上で開発中の `Manga Region Prompter（MRP）` です。

今回、生成結果画像そのものは添付しません。こちらで複数回の比較テストを行った結果を要約すると、現在のMRPは「各コマの内容をある程度分離する機能」としては明確に効果が出ています。特にControlNetでコマ枠構造を補助した場合、MRP有効時と無効時では内容の分離にかなり差が出ます。

一方、MRP単独ではモデル側が複数コマの内容を一枚のシーンとして融合しようとする傾向がまだ強くあります。とくにコマ数が増えた場合、単純なプロンプト文言だけではレイアウト固定に限界があります。

テストからは、おおむね以下の傾向が確認できました。

- `BREAK` によるチャンク分離は重要。
- 単なる改行そのものの影響は比較的小さい。
- `4koma`、`5koma` などはモデルにかなり強く構図を想起させる。
- `manga layout` 系はさらに強く、MRP単独では有効な場合がある。
- ただしControlNet併用時には `manga layout` 等が強すぎて、ControlNetの構造指定と競合する場合がある。
- `comic` 単独は比較的弱い。
- `PAGE:`、`STYLE:` のようなラベルそのものに明確な優位性は確認できず、トークンを消費する。
- Illustrious系モデルでは「画風・品質系 → ページ構造系 → 各コマ」という並びの方が自然に働いているように見える。
- コマの内容指定自体はMRPの領域分離によって一定程度効いており、今後は強いレイアウト文言を増やすより、MRP内部の領域管理を整理する方を優先したい。

以上から、現段階ではプロンプトテンプレートを大量に追加するより先に、MRP内部構造を整理します。

今回の主要目的は次の3点です。

1. PAGE / STYLE 周辺の構造整理
2. コマ領域とコマ番号を分離し、ユーザーが後から番号を交換可能にする
3. UI上の現在分かっている小さな導線問題も同時に修正する

---

## 1. 最重要：物理領域と論理コマ番号を分離する

現在、スライスや矩形作成を行った順序によって、ユーザーが意図したコマ番号と実際に割り当てられた番号が一致しない場合があります。

例：

- 画面右側をコマ1にしたい
- 左側をコマ2にしたい
- しかしスライス操作の結果、左がコマ1、右がコマ2になった

現状ではこれを修正するために矩形自体を作り直したり、プロンプト内容を手作業で交換する必要があります。

これは構造的に望ましくありません。

今後は、

「矩形そのもの」

と

「その矩形に割り当てられているコマ番号」

を別概念として管理してください。

概念上は以下のような構造を想定します。

```text
RegionGeometry
    stable_region_id
    x
    y
    width
    height
    mask / geometry information

PanelAssignment
    stable_region_id
    logical_koma_number

PanelContent
    logical_koma_number
    prompt
    weight
```

実際のクラス名・変数名は現在のコード構成に合わせて変更して構いません。

重要なのは、

「配列indexや作成順そのものをコマ番号として扱わない」

ことです。

矩形には作成後も変化しない内部IDを持たせてください。

例：

```text
region_A
region_B
region_C
```

それとは別に、

```text
region_A → koma 2
region_B → koma 1
region_C → koma 3
```

という割当を持てるようにしてください。

## 2. コマ番号交換機能を追加する

ユーザーが後からコマ番号を交換できるようにしてください。

例えば、

```text
左領域  = コマ1 / 赤
右領域  = コマ2 / 青
```

という状態で、

コマ1とコマ2を交換すると、

```text
左領域  = コマ2 / 青
右領域  = コマ1 / 赤
```

になります。

矩形の座標・サイズ・形状は変化させないでください。

これは「矩形移動」ではなく、

「論理コマ番号の再割当」

です。

---

## 3. 色はコマ番号に追従させる

現在使用しているコマ色は、論理コマ番号と一体として扱ってください。

例えば現行の色体系が、

```text
コマ1 = 赤
コマ2 = 青
コマ3 = 緑
コマ4 = 黄
コマ5 = 紫
...
```

であれば、コマ番号の交換時には色も自動的に交換してください。

つまり実装上は、

「赤色を別矩形へ移動する」

のではなく、

「コマ1を別矩形へ割り当てた結果、赤色表示も移動する」

という扱いが望ましいです。

色そのものを独立した状態として交換すると、将来的にコマ番号と色がずれる可能性があります。

可能であれば、

```text
color = colorForKomaNumber(koma_number)
```

のように論理番号から決定してください。

---

## 4. UI：現在の色付きコマカードをドラッグハンドルとして利用する

新しい大きな専用ウィンドウは現段階では不要です。

現在の各コマ情報カードには、

```text
[コマ1] コマ1
[コマ2] コマ2
```

のような色付き表示があります。

この色付き部分、またはその周辺をドラッグ可能な領域として明示してください。

例えばイメージとして、

```text
☷ [コマ1] コマ1
```

のようなドラッグハンドルを設けても構いません。

コマ1のハンドルをコマ3へドラッグした場合、

```text
コマ1 ↔ コマ3
```

を交換します。

交換対象は「カード表示位置」ではなく、

```text
logical_koma_number
```

です。

---

## 5. カードそのものの並び順変更とは区別する

カード全体をドラッグして単純に上下並べ替えるUIにはしないでください。

それを行うとユーザーから見て、

- 表示順を変えたのか
- プロンプト内容を交換したのか
- コマ番号を交換したのか
- 矩形自体を交換したのか

が分からなくなります。

今回実装するのはあくまで、

「キャンバス上の物理領域に割り当てられているコマ番号を交換する操作」

です。

カードの表示順自体は基本的に、

```text
コマ1
コマ2
コマ3
...
```

の論理番号順で構いません。

---

## 6. キャンバス表示も即時更新する

番号交換後はキャンバス側の、

- コマ番号
- 枠色
- 選択状態
- コマ情報カードの対応色

を即座に同期してください。

例：

交換前：

```text
左 = 赤 / コマ1
右 = 青 / コマ2
```

交換後：

```text
左 = 青 / コマ2
右 = 赤 / コマ1
```

見た目からも交換結果が明確に分かる必要があります。

---

## 7. プロンプト・weightも論理コマ番号に追従させる

非常に重要です。

例えば、

```text
koma 1:
red sports car

BREAK

koma 2:
green apple
```

という内容がある場合、

コマ1とコマ2の領域割当を交換した後は、

`red sports car`

が新しいコマ1領域へ効くようにしてください。

プロンプト文字列自体をコピーして交換するのではなく、

```text
PanelContent(koma1)
→ PanelAssignment(koma1)
→ region_B
```

という関係で処理する方が望ましいです。

同様に各コマのweightもコマ番号に紐付けてください。

---

## 8. メインプロンプト表示は論理コマ番号順を維持する

キャンバス上の位置が、

```text
左上  = コマ2
右上  = コマ1
左下  = コマ4
右下  = コマ3
```

のようになっても、メインプロンプト表示は基本的に、

```text
koma 1:
...

BREAK

koma 2:
...

BREAK

koma 3:
...

BREAK

koma 4:
...
```

という論理番号順を維持してください。

画面座標順にメインプロンプトを並べ替える必要はありません。

これは将来的な漫画の読み順指定にも利用できます。

例えば日本漫画的に、

```text
右上 = 1
左上 = 2
右下 = 3
左下 = 4
```

といった配置にしても、内部の論理順は正常に維持できます。

---

## 9. Undo / Redo対象にする

コマ番号交換操作はUndo / Redoへ含めてください。

例えば、

```text
コマ1 ↔ コマ3
```

を交換した後に「戻す」を押した場合、

元の割当へ戻る必要があります。

Undo対象には少なくとも、

- region → logical koma number の対応
- 選択状態
- 必要であれば表示状態

を含めてください。

---

# PAGE / STYLE構造の整理

今回の生成比較から、現在の

```text
PAGE
STYLE
各コマ
```

という考え方自体はUI上の整理としては有用ですが、最終プロンプト上で `PAGE:` や `STYLE:` という文字ラベルを付ける必要性は確認できませんでした。

さらにIllustrious系では、

「品質・画風系が先、構造指定が後」

の方が自然に働く可能性があります。

そのため、現在の内部2chunk方式は維持して構いませんが、最終的な出力順を整理してください。

推奨は、

```text
STYLE / QUALITY
BREAK
PAGE / STRUCTURE
BREAK
koma 1
BREAK
koma 2
...
```

です。

ただし、UI表示名称については現在の概念を残して構いません。

例：

```text
【全体画風・品質】
【ページ構造】
```

---

## 10. `PAGE:` / `STYLE:` の固定文字列は付加しない

現在または過去の版で、

```text
PAGE:
...
BREAK
STYLE:
...
```

のような出力をしている場合、固定ラベルそのものは出力しない方向でお願いします。

つまり、

```text
simple clean illustration, clear subjects
BREAK
4koma
BREAK
koma 1: ...
```

のようにします。

理由は、

- 明確な生成上のメリットが確認できない
- トークンを消費する
- モデルによっては単なる意味の薄い語として処理される

ためです。

UI上の「ページ構造」「画風・品質」という区分は残して構いません。

# ページ構造用デフォルトプロンプトについて

現段階ではテンプレート集の大幅変更は行いません。

ただしデフォルトのページ構造指定については、強すぎる語を避けてください。

テストでは、

```text
4koma
5koma
```

はかなり強く働きます。

さらに、

```text
4koma manga layout
5koma manga layout
```

はMRP単独ではかなり強力ですが、ControlNet併用時には構造指定が過剰になる場合があります。

そのためMRPの標準テンプレートとしては、

```text
4koma
```

または必要に応じて、

```text
4koma manga
```

程度までに留め、

```text
4koma manga layout
```

のような強い語を標準で自動投入するのは現段階では避けてください。

将来的に、

- MRP単独用
- ControlNet補助用

でテンプレートを分けることは検討します。

今回はそこまで実装しなくて構いません。

現在のスライス機能は、直近のテストでは良好に動作しています。

今回の改修によってスライス処理そのものを壊さないでください。

特に、

- 既存コマを横断して切断
- 縦方向切断
- 横方向切断
- スライス後の領域管理
- 自由矩形
- Exclusive領域
- 重なり領域

など、現在動いている機能は維持してください。

今回追加する「コマ番号再割当」は、これらとは独立した上位レイヤーとして扱うのが望ましいです。

# 表示切替ボタンのUI修正

別件ですが、小さなUI問題なので今回合わせて修正してください。

現在キャンバスの表示切替ボタンが、

現在カラー表示中なのに

```text
カラー表示
```

と表示されるなど、「現在の状態」を表示する形式になっています。

操作ボタンとしては導線が逆です。

ボタンには、

「押したら何になるか」

を表示してください。

つまり、

カラー表示中：

```text
白黒表示へ
```

白黒表示中：

```text
カラー表示へ
```

としてください。

内部状態そのものは変更不要で、表示文言と必要ならアイコンを修正してください。

# 実装時の注意

既存コードを確認したうえで、最小限の破壊的変更で実装してください。

とくに確認してほしいのは、

```text
region index
panel index
koma number
color index
prompt index
weight index
```

が現在同一の配列indexに依存していないかです。

もし例えば、

```python
panels[0] == koma1
panels[1] == koma2
```

という前提がコード全体へ埋め込まれている場合、今回の機能を単なる配列swapで実装しないでください。

一時的には動いても、自由矩形・重なり・読み順変更などを追加した際に再び破綻します。

内部的には、

```text
physical region
↓
logical koma assignment
↓
prompt / weight
```

の対応関係を明示してください。

# 最低限の動作確認

実装後、以下を確認してください。

## テスト1

左右2コマを作成。

```text
左 = コマ1
右 = コマ2
```

コマ1とコマ2をドラッグ交換。

結果：

```text
左 = コマ2
右 = コマ1
```

になる。

矩形位置は動かない。

## テスト2

コマ1：

```text
red sports car
```

コマ2：

```text
green apple
```

交換後、メインプロンプト表示は、

```text
koma 1: red sports car
BREAK
koma 2: green apple
```

を維持する。

ただし生成時の適用領域は交換されている。

## テスト3

コマ1とコマ3を交換。

- 色
- キャンバスラベル
- prompt
- weight
- 選択
- 生成用領域

が一致すること。

## テスト4

Undo。

交換前へ完全に戻ること。

Redoで再度交換されること。

## テスト5

自由矩形・スライス・重なりを含む5コマ程度を作成し、番号交換後も矩形形状が変わらないこと。

## テスト6

カラー表示中のボタンが、

```text
白黒表示へ
```

になり、押すと、

```text
カラー表示へ
```

へ変わること。

修正後は単に「完了しました」だけではなく、以下を報告してください。

1. 主に変更したファイル
2. コマ番号と矩形IDをどのように分離したか

4. promptとweightの紐付け方式
5. Undo / Redoへの追加方法
6. PAGE / STYLEの最終出力順をどう変更したか
7. `PAGE:` / `STYLE:` 固定ラベルを削除したか

今回の改修で重要なのは、単に「コマを入れ替えられるボタンを追加する」ことではありません。

MRP内部で、

```text
矩形の物理配置
≠
コマの論理番号
```

という関係を成立させることが本質です。

ここを今の段階で整理しておくことで、今後の変則コマ割り、5～6コマ、自由矩形、重なり、漫画の読み順指定などへ拡張しやすい構造にしてください。
